## Dialograph的简介

[Dialograph](https://github.com/qinghuan-yu/Dialograph) 是我在 2026 年五月建立的项目，现在也成为了我的课设作业。它读取本地的对话导出文件，尝试从长期聊天里整理沟通节奏、关系动态、人物印象和互动边界。

最初的实现可以概括为：预处理、分块、交给 LLM 阅读，再汇总证据和反例，形成人物的侧写。

这篇文章先介绍项目目前怎么工作，再谈谈我为什么讨厌它。

本地网页由 Python 服务提供。2026 年 11 月这次更新，把报告生成进一步拆成了原文选取、结论账本和本机校验，网页也可以直接回查每条结论引用的对话。

## 分析链路

完整工作流可以概括为：

```text
本地对话导出
  → 格式适配与私聊身份校验
  → 本机规则脱敏
  → 消息解析、清洗、时间排序与诊断
  → 统计与长期会话建模
  → 连续分块及提示词预算检查
  → LLM 逐块提取结构化证据
  → 引文原文绑定与歧义隔离
  → 阶段总结与证据总表
  → 候选事件选材，补齐连续原文
  → 原文覆盖不足时规划命题并检索完整会话
  → 关系与人物结论 JSON
  → 本机校验出处、时间、动作结构和适用范围
  → 编译两份报告与结论账本，默认交付待人工确认稿
```

### 预处理与统计

预处理会记录原始消息数、有效消息数、跳过原因、时间异常和重排序情况。

长期会话建模以四小时间隔划分会话，统计谁发起、谁收尾、消息数量、会话时长和会话内回复速度。

### 长对话分块阅读

当前工作流按时间顺序连续分块，并同时约束消息数量、原文字节数和实际提示词字节数。分块阶段要求模型输出紧凑的 JSON 证据，减少中间长文导致的截断和格式错误。

项目会保存分块覆盖清单，核对全部有效消息都被连续提交过。报告阶段再选取连续原文，并记录入选和省略范围。分块阅读与最终选材分别留有覆盖记录。

### 五类证据

分块输出分为五类：

| 类别 | 作用 |
| --- | --- |
| `events` | 记录具体事件 |
| `relation_signals` | 整理支持或反驳关系解释的信号 |
| `persona_signals` | 整理人物印象与表达风格信号 |
| `counter_evidence` | 单列反证与边界条件 |
| `uncertainties` | 保留不能判断的问题 |

## 证据回到原话

当前版本为消息和证据生成编号，并在本地核对模型引用的原话。引文必须在当前分块中找到唯一、连续、逐字一致的位置，才会作为已匹配的证据进入后续材料。

没有找到原文的条目标记为 `unmatched`；同一句话出现多次、无法唯一定位的条目标记为 `ambiguous`。它们会留在隔离清单里，供人工回查，不进入证据摘要和阶段总结。存疑问题单独保留。

## 从证据到结论

### 连续原文与命题检索

报告先从完整证据总表构建候选事件单元，围绕引文回填前后各 16 条消息，并向外补齐边界上的发言轮次。结构化摘要和原文窗口共用同一份选择结果，支持信号、反证和存疑一起参与选材。

如果当前材料没有覆盖候选事件所需的原文，流程会先列出待判断命题，再按支持和挑战两个方向检索，提供命中的完整会话。默认连续原文预算为 48,000 字节，`complete_if_fits` 模式可在配置预算内提供整份脱敏原文。

进入命题检索后，关系报告和人物侧写分别依据入选原文生成。普通选材路径的人物侧写仍会参考关系报告中的解释，作为待核对线索。

### 结论账本与本机编译

模型先输出结论 JSON。结论账本 v3 为每条判断记录对象、事实或推断类型、局部或长期范围，以及支持证据、反证和情境限制。程序据此校验来源和字段，再生成 Markdown 正文。

原话、发言者和日期由程序复制，消息间隔由程序计算。动作单独记录意向、自述完成和结果确认，报告分别展示原文事实与模型解释。读者可以从解释中的引用回到对应消息，查看它实际支持了哪一句判断。

网页和完整命令行默认采用 `human` 模式，报告带有“待人工确认”状态。程序检查出处与结构，解释由读者结合原文核对。选择 `--review-mode model` 后，会增加逐条模型复核和有界修订。

## 工程结构与失败恢复

项目以 Python 工作流为核心，本地网页和命令行共用分析服务。主要职责分布如下：

| 模块 | 职责 |
| --- | --- |
| `conversation_formats.py`、`conversation_input.py` | 格式适配与私聊输入校验 |
| `privacy_redaction.py`、`analyze.py` | 脱敏、解析、诊断、统计和会话建模 |
| `analysis_service.py` | 共用的结果复用、续跑选择与生成决策 |
| `chunk_pipeline.py`、`llm_client.py` | 分块执行、模型请求和错误恢复 |
| `evidence_validation.py`、`evidence_grounding.py` | 证据结构校验、原文绑定与核验 |
| `prompt_budget.py`、`report_generation.py` | 材料预算与报告输入准备 |
| `report_context.py`、`claim_retrieval.py` | 事件选材、连续原文和命题检索 |
| `claim_ledger.py`、`claim_compiler.py`、`claim_facts.py` | 结论生成、出处与结构校验、事实回填和报告编译 |
| `evidence_store.py`、`web_evidence.py` | 本地证据索引、关键词查询与原文回查 |
| `workflow_state.py`、`run_promotion.py`、`artifact_audit.py` | 缓存身份校验、结果发布与完整性审计 |

这些模块把长时间分析拆成可保存的运行过程。一次运行会保留分块结果、证据、阶段总结、报告输入、结论账本和参数。模型请求的 token 用量与缓存命中情况也有独立记录。

遇到部分可恢复的分块请求错误时，工作流会缩小分块和提示词预算，为当前对象新建一次运行并重试。

## 输出与隐私

主要输出是关系动态报告、人物侧写报告、两份结论账本，以及包含来源信息的结构化证据总表。命令行默认写入 `analysis/`；网页任务使用独立的 `analysis/web_jobs/{job_id}/`，保存输入快照、状态与结果，避免覆盖命令行报告。网页也支持停止和继续任务。

网页提供“查找对话线索”，通过本地 SQLite/FTS5 索引按关键词查找支持候选、反证、混合信号和存疑。点击引用可查看脱敏原文、高亮引句、时间和消息序号。报告中的原文事实默认收起，下载的 Markdown 包含完整引文。

当前版本默认在本机替换双方昵称、账号、常见电话、邮箱、证件号、银行卡号和链接，并允许补充需要隐藏的词。原始导出和任务输入快照仍保留在本机。`talks/`、`analysis/` 等私人数据目录默认由 Git 忽略。

## 但是我为什么讨厌Dialograph

做这个项目的起因很简单。我觉得身边缺一个能稳定、准确地看清人际关系的工具，于是想自己动手做一个，把周围那些说不清的关系理一理。

工具做得很快。思路前面已经讲过了。技术上并不是多难的事情。

但是现在回头看，必须反思。看到“回避倾向”“主动付出”这类结果，确实能换个角度看自己。但关系是要先验的，然后再是分析。把一段独一无二的相处压成数字，读起来就是冷的，证据再扎实也一样。

我为此付出了代价。有两段于我而言很重要的关系，就是因为我不合时宜的求知欲而分崩离析。我习惯于用分析和数据来获得安心，但现在看来，其程度已经超出了界限。就像是把需要感性体会的关系量化成不切实际的数字，用百分比告诉你是否在关系里处于主动付出，这本身就不合常理。

所以请记住，请尊重边界。在关系里请先感受，再分析。分析可以是事后的补充，但不该成为理解一个人的起点。

>如果你读到了这里，我多说一句：别让自己变成什么事都要靠分析才能安心的人，那很累。
