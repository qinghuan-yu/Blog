## 第一章：操作系统引论

### 第一部分：操作系统是什么？它有什么特征？

可以把计算机硬件（CPU、内存、硬盘）想象成一家拥有各种设备的**工厂**，而操作系统负责统一管理与调度这些硬件资源。

#### 1. 操作系统的作用与功能

操作系统统一管理硬件资源，为应用提供运行环境，也让用户更方便地使用计算机。它的作用主要体现在以下三个层面。

1. **作为用户和计算机硬件之间的接口（对外）：** 不需要用二进制代码去控制硬盘磁头读取数据，只需要双击鼠标打开一个文件。OS把复杂的硬件操作封装成了简单的命令。

2. **作为计算机系统资源的管理者（对内）：** 工厂里有很多任务要干，但资源有限。OS的四大主要功能（1.5节）就是管好这些资源：
   
   - **处理机管理（管CPU）：** 决定现在哪个程序可以使用CPU运行。
   
   - **存储器管理（管内存）：** 决定哪个程序的数据可以放在内存里，放在哪里，谁也不能越界。
   
   - **设备管理（管I/O）：** 管好键盘、鼠标、打印机等设备的输入输出。
   
   - **文件管理（管数据）：** 把硬盘上的物理数据块组织成能看懂的文件夹和文件。

3. **扩充裸机（抽象）：** 在裸机（纯硬件）上覆盖一层软件，把它变成一台功能更强大、更容易使用的“虚拟机”。
   
   ----

#### 2. 操作系统的四大基本特性（1.3 节）

这是OS区别于普通软件（比如微信、Word）的最核心特征。

- **① 并发**
  
  - **原理：** 指两个或多个事件在**同一时间间隔内**发生。在宏观上看，好像有多个程序在同时运行；但在微观上（单核CPU），任何一个时刻其实只有一个程序在运行，CPU只是在它们之间**极速切换**，制造了“同时”的假象。
  
  - **注意区分并发与并行：** 并行是指两个或多个事件在**同一时刻**发生（比如多核CPU，每个核同时跑一个程序）。

- **② 共享**
  
  - **原理：** 系统中的资源可供内存中多个并发执行的进程共同使用。
  
  - 分为两种：**互斥共享**（比如打印机，我用的时候你不能用，必须排队）和**同时访问**（比如硬盘上的一段公共代码，多个程序可以宏观上“同时”读取）。

- **③ 虚拟**
  
  - **原理：** 把一个物理上的实体，变成若干个逻辑上的对应物。
  
  - **例子：** 物理上只有一个CPU，但通过操作系统的“时分复用”技术（大家轮流快速用），每个程序都觉得自己独占了一个CPU。虚拟内存按需把部分页面放入物理内存，其余由文件或交换区提供后备存储，因此进程的虚拟地址空间总量可以超过物理内存容量。

- **④ 异步**
  
  - **原理：** 因为系统中有多个程序在并发执行，大家都在争抢资源。所以程序会走走停停，分段执行。每个程序何时开始、何时暂停、何时结束，以怎样的速度推进，都是**不可预知的**。
    
    ----

### 第二部分：操作系统是如何演进的？它的底层运行机制是什么？

#### 1. 发展过程 (1.2 节)

操作系统的演进围绕资源利用、任务调度和交互需求展开，可以从几个关键阶段理解：

- **单道批处理 -> 多道批处理系统 ：这是质的飞跃。**
  
  - **痛点：** 以前CPU很快，但输入输出（I/O，比如读写磁带）极慢。如果一个程序在等I/O，CPU就只能干瞪眼（空闲）。
  
  - **解决原理（引入并发）：** 内存里同时放多个程序。程序 A 等待 I/O 时，OS 立即将 CPU 切换给程序 B 使用。这也是**并发**机制的起源，核心目的是**提高资源利用率**。

- **多道批处理 -> 分时系统 ：为了“人机交互”。**
  
  - **痛点：** 批处理系统虽然效率高，但用户把任务交上去后就失去控制权了，没法在中途修改。
  
  - **解决原理（时间片轮转）：** 像切蛋糕一样把CPU时间切成极短的“时间片”（比如几十毫秒）。每个用户轮流用一个时间片。这就好比你在电脑上挂着后台脚本，同时还能流畅地打游戏，因为系统在极速切换，给你一种你独占电脑的错觉。
    
    ----

#### 2. 操作系统的运行环境 (1.4 节)

这一节关注**如何防止用户程序的错误或越权操作破坏整个系统。**

为了安全，CPU在硬件级别提供了支持，这就是**双重工作模式 (1.4.3)**。

- **用户态（目态）：** 普通应用程序运行的环境。在这个状态下，CPU只能执行**非特权指令**（比如加减乘除）。

- **核心态（管态/内核态）：** 这是操作系统内核运行的环境。在这个状态下，CPU可以执行**特权指令**（比如修改页表基址、设置中断屏蔽、访问受保护的设备控制寄存器）。

**保护规则：** 用户态执行特权指令会触发异常，由内核处理。读写无权限的内存则属于地址映射或访问权限检查的问题，普通访存指令也可能触发异常。内核根据原因决定恢复执行、报告错误或终止进程。

那么问题来了，用户程序在用户态，操作系统在核心态。如果用户程序真的需要读写硬盘（比如保存一个文件），它自己又没有权限，怎么办？
这就必须依赖**1.4.4 中断与异常**。

在操作系统中：

- **中断是操作系统夺回 CPU 控制权的核心机制。**

- **广义的中断分为两种：**
  
  1. **外中断（狭义的中断）：** 来自CPU外部的硬件信号。比如你敲击了一下键盘，或者定时器到点（时间片用完）了。
  
  2. **内中断（异常）：** 来自CPU内部执行指令时产生的问题。比如程序算术除以0，或者程序**主动**发起特殊的指令请求操作系统帮忙（这叫“陷入指令”）。

**基本机制：** CPU 响应中断或异常时保存必要的执行现场，转入内核处理入口。事件发生在用户态时会切换到内核态；发生在内核态时仍在内核中处理。可屏蔽中断的响应还受中断屏蔽状态等条件影响。

### 第三部分：系统调用、实时系统与内核组织

**系统调用**是应用请求内核服务的接口，例如创建进程、打开文件、申请映射。一次调用通常经历：准备调用号和参数 → 执行陷入指令 → 内核检查参数与权限 → 完成服务或等待事件 → 返回结果。

库函数与系统调用不一一对应。`strlen` 可以完全在用户态计算；`printf` 可能先写用户态缓冲区，稍后才通过 `write` 请求内核。进入内核是**模式切换**；若内核继续为原线程服务，未必发生进程或线程切换。

| 分类角度 | 类型 | 主要特点 |
| --- | --- | --- |
| 服务目标 | 批处理 | 重视吞吐量与周转时间 |
| 服务目标 | 分时 | 重视交互响应与公平性 |
| 服务目标 | 实时 | 重视截止期限；硬实时要求满足关键期限，软实时允许一定程度的超期 |
| 内核组织 | 宏内核 | 文件、内存、设备等主要服务在内核空间运行，调用路径直接 |
| 内核组织 | 微内核 | 内核保留调度、通信等基本机制，部分服务在用户空间运行，通过消息协作 |

模块化内核可以动态装卸驱动等模块。模块化描述组织方式，与服务是否运行在内核态是两个维度。

## 第二章：进程的描述与控制

### 第一部分：进程基础与状态转换

#### 1. 为什么要有“进程”？它和“程序”有什么区别？

- **程序**：是静态的，即存放在磁盘上的代码与数据文件。

- **进程**：是动态的。当你双击运行这个程序，操作系统把它加载到内存中，并分配了资源开始执行时，它就成了一个进程。**进程是资源分配的基本单位；引入内核线程后，处理机通常以线程为调度单位。**

#### 2. “快照”到底是什么？—— PCB（2.2.4 进程管理中的数据结构）

操作系统要同时管理几百个并发的进程，它必须有一套账本。所谓“快照”，在操作系统中被称为 **PCB（进程控制块）**。

PCB 可以视为一个结构体，记录了操作系统管理进程所需的全部信息：

- **进程标识符：** 也就是进程的身份证号。

- **处理机状态：** 当进程被剥夺CPU时，CPU里面的各种寄存器（比如**程序计数器 PC** 记录着恢复执行所需的指令地址、通用寄存器里算到一半的数据）必须全部原封不动地保存到 PCB 中。这与硬件中断处理中的现场保护类似：中断触发时先保存当前寄存器上下文，待重新调度时再恢复。

- **进程调度信息：** 这个进程的优先级是多少？它已经等了多久了？

- **进程控制信息：** 它的代码和数据在内存的哪个物理位置？它打开了哪些文件？

**PCB 是内核识别和管理进程的依据。** 创建进程还要建立地址空间、初始化现场和资源引用，再加入调度队列；终止进程要释放资源，并保留必要的退出状态供父进程回收。PCB 的建立与撤销只是生命周期管理的一部分。

#### 3. 进程的状态与转换 (2.2.2 - 2.2.3)

进程不是一直在一刻不停地运算的。因为它要和别的进程抢 CPU，还要等硬盘、等网络，所以它的一生都在几个状态之间不断切换。

进程在执行过程中主要有**三个基本状态**：

1. **运行态：** 进程不仅拥有自己需要的所有资源，而且**正在 CPU 上执行代码**。（在单逻辑处理器的教学模型中，同一时刻只有一个调度实体运行）。

2. **就绪态：** 万事俱备，只欠东风。进程已经拥有了除 CPU 之外的所有资源，已经具备继续执行所需的条件，**只要获得 CPU，它就能继续执行**。所有的就绪进程会排成一个“就绪队列”。

3. **阻塞态：** 进程在等待某个事件发生（比如等待玩家输入一段文字、等待网络下载一张图片、等待硬盘读取数据）。**等待的事件发生后，进程才能回到就绪态，重新参与 CPU 调度。**

![进程的三个基本状态：就绪经调度进入运行，运行可因抢占回到就绪或因等待事件进入阻塞，阻塞在事件发生后回到就绪](/images/notes/operating-system/process-states.svg)

举个打游戏的例子：

- 你正在全神贯注操作角色打 Boss（**运行态**）。

- 突然游戏提示“正在连接服务器...”，你在等网络数据包，这时候你什么都操作不了，CPU在游戏里也无事可做（**阻塞态**）。

- 网络数据包到了，连接成功！但此时恰好系统把 CPU 时间片分给了后台正在下载文件的迅雷。你的游戏虽然可以继续玩了，但还没轮到它用 CPU（**就绪态**）。

**“阻塞态”的类比：** 菜炒到一半，你突然发现**没盐了**。为了继续这道菜，你必须掏出手机点个外卖送盐。
在外卖小哥（慢速的外部 I/O 设备，如硬盘、网络）把盐送达厨房之前，你**完全无法**继续炒这道菜。此时这道菜只能被迫停火，盖上锅盖放在一边（**进入阻塞态**）。
在这个漫长的等待期里，为了不浪费时间，你转身去切另一道菜的配料（**CPU 发生了上下文切换，去执行另一个就绪态的进程**）。等外卖员敲门（**硬件中断**），这道菜才重新拥有了继续做下去的条件，回到**就绪态**排队。

##### 进阶：挂起状态（Swap）

进程状态模型还可以加入挂起状态，把就绪和阻塞分别细分为驻留内存与换出内存两种情况。其中，“静止就绪”和“静止阻塞”表示进程处于挂起状态。

**痛点与风险：**

假设你开了 100 个网页，还开了个 3A 大作。此时**内存爆满了**。

那些处于“阻塞态”（比如正在等网络下载）或者“就绪态”（排队等 CPU）的进程，代码和数据仍占用物理内存。在内存紧张时，这会影响其他进程获得所需空间。

**解决原理（这就是挂起）：**

此时操作系统会将暂时不运行的进程的数据（部分实现也包括部分控制信息）从内存**换出到磁盘交换区（Swap）**，腾出物理内存供急需的进程使用（PCB 本身通常仍常驻内存以便跟踪状态）。

- 被踢到硬盘上的就绪进程：**静止就绪**。

- 被踢到硬盘上的阻塞进程：**静止阻塞**。

当内存空余了，或者该它运行了，操作系统再把它从硬盘读回内存，这叫**激活**。

#### 进程控制原语与上下文切换

创建、终止、阻塞和唤醒要一致地维护 PCB、资源引用和队列。阻塞时，线程登记等待事件并移出可运行队列；事件完成后，唤醒操作把它移回就绪队列，随后才有机会被调度。检查事件与进入等待队列必须配合同步，否则可能发生“事件已到、线程却刚开始睡”的丢失唤醒。

上下文切换保存当前执行状态，再恢复下一个任务的寄存器、栈和必要的地址空间信息，会产生调度与缓存开销。进入系统调用后仍为原线程执行，是模式切换；阻塞后换另一个线程运行，才涉及任务切换。

以 Unix 接口理解生命周期：`fork` 创建子进程，`exec` 用新程序替换当前进程映像，`exit` 结束执行，`wait` 回收子进程退出信息。`exec` 本身不创建新进程。子进程已退出、退出信息尚未回收时称为僵尸进程。

### 第二部分：并发风险与进程通信

本节讨论**前趋图与并发风险（2.1 节）**以及**进程通信（2.4 节）**。

#### 1. 并发执行的客观风险：为什么要画“前趋图”？

并发看起来很美好（宏观上同时运行），但它引入了极高的系统复杂度和风险。

- **封闭性和可再现性被破坏：** 如果程序 A 和程序 B 并发执行并共享同一变量 `x`，由于推进顺序受调度影响（异步性），同一程序以相同输入运行两次可能得到不同结果。

- **前趋图的作用：** 用有向无环图表示执行顺序：节点代表程序或操作，箭头表示先后依赖。若有从 A 指向 B 的箭头，B 就要在 A 完成后执行。并发执行时，调度与同步机制需要维持这些依赖关系。

![操作 A 与 B 可并发，操作 C 需要等待两者全部完成，箭头表示先后依赖](/images/notes/operating-system/precedence-dag.svg)

#### 2. 进程通信

**基本背景：** 操作系统为保证安全性，将各个进程的地址空间相互隔离，进程 A 不能直接访问进程 B 的私有内存。当多个进程需要协同工作并交换数据时，必须通过操作系统提供的**进程间通信（IPC）**机制。

操作系统提供了三种主要的“合法”通信渠道：

1. **共享存储：** 操作系统在内存里划出一块“公共黑板”。进程 A 把数据写在黑板上，进程 B 直接去读。
   
   - *特点：* **速度最快**，因为不需要把数据拷来拷去。
   
   - *风险：* 读写冲突。如果 A 正在写，B 同时跑去读，读到的就是错乱的半截数据。必须引入复杂的互斥锁（下一章的难点）。

2. **管道通信：** 在进程之间建立一个单向字节流缓冲区（类似单向水管），一个进程从写端写入字节流，另一个进程从读端读取。
   
   - *特点：* 普通管道通常是单向字节流。阻塞读写会等待数据或空间；非阻塞模式会返回当前可处理的结果，或报告暂不可用。

3. **消息传递：** 进程把数据打包成一个个特定格式的“信件”，通过操作系统内核里的“邮局”发送给目标进程。

#### 场景分析：高吞吐渲染与计算进程的通信

考虑一个对吞吐量和延迟要求较高的图形系统：

- **进程 A：** 负责高频计算多边形顶点的物理坐标变化。
- **进程 B：** 负责接收这些坐标数据并提交给显卡渲染。

当两个独立进程每秒需要交换大量数据时，通常选择**共享存储**而非管道或消息传递：

- **选择理由：** 管道与消息传递都需要将数据从发送进程复制到内核缓冲区，再从内核缓冲区复制到接收进程，高频大数据量下拷贝开销可观。而在共享存储方式中，操作系统将同一块物理内存同时映射到进程 A 和进程 B 的虚拟地址空间。映射建立后，进程 A 直接写入该区域，进程 B 直接从同一区域读取，无需内核中转复制。

#### 共享存储中的同步问题

共享存储需要处理读写交错的问题。多个进程访问同一数据，结果随执行顺序变化，这类问题称为**竞态条件**。

使用共享存储时，需要另外协调读写：**共享区域本身不提供访问同步。**

- **读写交错的例子：** 进程 A 正在更新共享内存里的模型坐标，写完上半身坐标后被切走。此时 B 读取整个模型，得到的是上半身的新坐标和下半身的旧坐标，渲染结果就会错位。

- **同步方式：** 可以用**互斥锁**或**信号量**保护共享数据。A 持锁写入时，B 等待；A 写完并释放锁后，B 再读取完整结果。设计多把锁时，还要安排一致的获取顺序，防止进程互相等待对方持有的锁。

### 第三部分：关于线程

#### 1. 为什么需要线程？

进程通过地址空间隔离提供了良好的安全性，但进程创建、切换和通信也伴随着较大的**性能开销**。

想象正在进入一个包含很多效果的网页：

1. 监听并响应用户的鼠标滑动和点击。

2. 渲染 CSS 粒子动画。

3. 在后台通过网络请求拉取最新的数据。

如果按照第一章的“并发”思路，把这三件事变成三个独立的**进程**会怎样？

- **进程切换开销：** 在不同进程间切换时，操作系统需要保存和恢复执行上下文，并切换地址空间。频繁切换会增加这部分开销。

- **进程间通信：** 动画进程使用网络进程取回的数据时，需要通过共享存储、管道等机制传递，并协调读写顺序。

为了解决这个问题，计算机科学家在进程的内部，又切分出了更细的执行单位，叫**线程**。

#### 2. 进程与线程的区别

区分进程和线程，可以从资源分配与执行调度两个角度入手：

- **进程：是操作系统分配资源的基本单位。** 它就像是一个**封闭的车间**（拥有独立的内存空间、打开的文件、各种硬件资源）。

- **线程：是 CPU 调度和执行的基本单位。** 它就像是车间里的**流水线工人**。

**关键特征与原理：**

1. **资源归属：** 线程自身仅维护运行必需的少量状态（线程控制块 TCB、程序计数器、寄存器集合和栈空间），其余系统资源均归所属进程所有。

2. **地址空间共享：** 同一进程下的所有线程共享该进程的内存地址空间和打开的文件。线程 A 写入进程内存的数据，线程 B 可以直接读取，无需经过内核通信接口。

3. **切换开销小：** 同一进程内的线程切换不需要切换页表（地址空间不变），只需保存和恢复寄存器上下文与栈指针，因此开销远低于进程切换。

![进程拥有独立地址空间，内部线程共享代码、数据和文件，各自保留 PC、寄存器和栈](/images/notes/operating-system/process-thread-resources.svg)

#### 3. 多线程的风险与同步要求

由于多个线程共享同一地址空间，多线程程序需要额外处理隔离性与同步问题：

- **风险一：线程错误影响整个进程。** 线程共享进程的地址空间。如果负责拉取网络数据的线程发生内存访问越界，所引发的异常可能导致整个进程退出，网页或游戏也会随之关闭。

- **风险二：并发访问共享数据。** 线程 A 修改变量 `x` 时，线程 B 同时读取或修改它，结果会受执行顺序影响。**线程同步与互斥锁**用于协调这些访问，保护共享状态。
  
  ---

#### 4. 用户级线程与内核级线程

| 映射方式 | 谁管理线程 | 阻塞与并行特点 |
| --- | --- | --- |
| 多对一 | 用户线程库管理多个线程，内核只见一个调度实体 | 传统阻塞系统调用会阻塞整个实体，无法靠这些用户线程利用多核并行 |
| 一对一 | 每个用户线程对应一个内核线程 | 一个线程阻塞时其他线程仍可运行，可分派到多个 CPU 核 |
| 多对多 | 多个用户线程复用多个内核线程 | 用户态与内核调度配合，可控制内核线程数量，运行库实现更复杂 |

协程常由运行库在用户态调度，与线程的对应关系由运行库决定。线程共享进程的地址空间，各自保留寄存器现场和栈，共享数据仍需要同步。

IPC 还常用**套接字**传输本机或跨机器的数据，用**信号**通知事件。普通匿名管道通常提供单向字节流，阻塞读写会等待数据或空间，非阻塞方式可立即返回暂不可用。

## 第三章：处理机调度

这一章讨论 **CPU 调度算法**。多个进程竞争 CPU 时，调度器要决定由谁先运行、每次运行多久，以及如何兼顾响应速度和系统吞吐量。

本节介绍调度的层次划分与常用调度算法。

### 第一部分：调度的三个层次

操作系统调度不是一刀切的，它分为三个级别，就像医院看病一样：

- **① 高级调度（作业调度）：从硬盘 -> 内存**
  
  - *原理：* 硬盘里有一堆程序排队等着运行。高级调度就是决定把哪些程序从硬盘调入内存，给它们创建 PCB，变成“就绪态”。
  - *比喻：* 医院大门外的保安，决定今天放哪些病人进医院大厅排队。发生频率**最低**（几分钟一次）。

- **② 中级调度（内存调度）：内存 <-> 硬盘（挂起区 Swap）**
  
  - *原理：* 对应第二章介绍的**挂起与激活**。当内存紧张时，将暂时不运行的进程换出到磁盘挂起区；当内存充裕时，再将其换入内存。
  - *比喻：* 医院大厅人太多了，护士把一些病情不急的病人先赶到院子外的长椅上等，大厅空了再叫进来。发生频率**中等**。

- **③ 低级调度（进程调度）：内存（就绪队列） -> CPU**
  
  - *原理：* **这是整个操作系统最核心、最频繁的动作。** 决定从就绪队列中挑哪一个进程，把 CPU 的控制权交给它。
  - *比喻：* 诊室里的医生，喊门外排队的人：“下一个，张三！”。发生频率**极高**（每秒钟成百上千次）。

**注意：** 本章后续讨论的调度算法，通常均指**低级调度（进程调度）**。

![高级调度接纳作业，中级调度管理换入换出，低级调度从就绪队列分派 CPU](/images/notes/operating-system/three-scheduling-levels.svg)

### 第二部分：常见调度算法

不同调度算法在响应时间、周转时间和公平性之间做出的取舍不同。先看三种基础算法：

**① 先来先服务**

- *原理：* 谁先排队，谁就先用 CPU，用到结束或者用到自己阻塞为止。
- *代价：* **护航效应**。假设一个视频渲染进程要连续使用 CPU 10 小时，后面跟着 100 个只需要 1 毫秒的打字响应进程，短任务就会长时间等待。只要排在前面的任务在有限时间内结束或阻塞，后面的任务就能轮到 CPU。饥饿则指任务因调度规则而长期得不到服务。

**② 短作业优先**

- *原理：* 预测哪个进程需要的运行时间最短，就先给谁安排 CPU。
- *优势：* 在一批作业同时到达、运行时间已知且采用非抢占调度的条件下，短作业优先可以使这批作业的**平均等待时间最短**。
- *代价：* **长作业饿死**。如果系统里源源不断地涌入短任务，那个需要算 10 小时的视频渲染进程可能**永远**也分不到 CPU。而且操作系统其实根本无法准确预测一个进程到底要跑多久。

**③ 时间片轮转（RR）**

- *原理：* 同一就绪队列中的进程轮流使用 CPU。系统给每个进程一个固定大小的“时间片”（比如 10ms）。时间片用完且任务仍可运行时，通过硬件定时器中断触发调度，将进程放回队尾，等下一轮。
- *优势：* 解决了 FCFS 的护航效应，也解决了 SJF 的饿死问题。用户交互体验通常更好。
- *代价：* **上下文切换开销**。如果时间片太短（比如 0.1ms），CPU 会花大量时间在保存 PCB、恢复 PCB 上，真正用于业务计算的时间反而变少，系统总效率会明显下跌。

#### 拆解：优先级调度算法

顾名思义，就是给每个进程发一个“VIP 等级”。调度时永远先挑 VIP 等级最高的进程执行。

**核心考点与风险分析：**

1. **抢占式优先级 vs 非抢占式优先级**
   
   - 假设正在运行一个 VIP 3 的进程，此时就绪队列突然来了一个 VIP 5。
   - 如果是**非抢占式**：VIP 5 只能排队，等 VIP 3 结束、阻塞或主动让出 CPU。
   - 如果是**抢占式**：高优先级任务就绪后，调度器可在允许抢占的时机保存当前现场，转而运行它。实时系统常用抢占调度，以满足紧迫任务的截止期限。

2. **调度风险：饥饿**
   
   - 这是优先级调度的最大痛点。如果系统不断涌入高优先级进程（比如 VIP 4、VIP 5），低优先级进程可能在就绪队列里**永远等不到 CPU**。
   - **如何解决饥饿：老化机制**。一个进程在就绪队列里等待越久，系统就逐步提高它的优先级。比如 VIP 1 等 10 分钟提到 VIP 2，等 1 小时再提到 VIP 5。这样只要等待足够久，低优先级进程最终也能得到执行机会。

#### 周转时间与带权周转时间计算

调度算法大题通常要求画时间轴、算平均值，光背概念还不够。

你只需要记住两个公式：

```text
周转时间 = 完成时刻 - 到达时刻
带权周转时间 = 周转时间 / 服务时间
```

周转时间回答的是：这个作业从进系统到彻底完成，一共在系统里待了多久。

带权周转时间回答的是：从到达到完成所用的总时间，是自身服务时间的多少倍。它包含执行时间，不只是排队等待。

举个小例子：

```text
P1：到达 0，运行 8
P2：到达 0，运行 6
P3：到达 0，运行 12
P4：到达 0，运行 4
```

如果用非抢占优先级调度，并且数值越小优先级越高，假设优先级顺序是：

```text
P2 -> P1 -> P4 -> P3
```

时间轴就是：

```text
0      6      14     18      30
|  P2  |  P1  |  P4  |  P3   |
```

![按 P2、P1、P4、P3 顺序执行的比例甘特图，完成时刻分别为 6、14、18、30](/images/notes/operating-system/scheduling-gantt.svg)

完成时刻：

```text
P2 = 6
P1 = 14
P4 = 18
P3 = 30
```

因为它们都在 0 时刻到达，所以周转时间就等于完成时刻。

平均周转时间：

```text
(6 + 14 + 18 + 30) / 4 = 17
```

带权周转时间：

```text
P2 = 6 / 6 = 1
P1 = 14 / 8 = 1.75
P4 = 18 / 4 = 4.5
P3 = 30 / 12 = 2.5
```

平均带权周转时间：

```text
(1 + 1.75 + 4.5 + 2.5) / 4 = 2.4375
```

计算步骤：**先画时间轴，确定各作业的完成时刻，再代入公式求周转时间与带权周转时间。**

下面以**多级反馈队列**为例，将优先级和时间片结合起来。

1. **队列 1（最高优先级，时间片很短，比如 10ms）**
   
   - 所有新任务先进入队列 1。
   - *效果：* 短任务可以在前几个时间片内快速完成，实现**低延迟响应**。

2. **队列 2（中等优先级，时间片较长，比如 50ms）**
   
   - 如果任务在队列 1 的时间片内反复跑不完，系统会把它降级到队列 2。

3. **队列 N（最低优先级，常用 FCFS 或超长时间片）**
   
   - 连续多次跑不完的长任务最终会落到底层队列。上层队列为空时，底层任务获得较长的 CPU 时间，以减少频繁切换的开销。

**多级反馈队列根据任务的运行情况调整优先级，兼顾短任务的响应与长任务的执行，无需预先知道任务时长。若高优先级任务持续到来，还需配合优先级老化或定期提升等机制，防止低优先级任务饥饿。**

### 第三部分：评价指标与算法补全

设到达时刻为 $a$、首次获得 CPU 的时刻为 $s$、完成时刻为 $f$、总 CPU 服务时间为 $b$：

- 响应时间：$s-a$，描述首次得到服务有多快。
- 周转时间：$f-a$；带权周转时间：$(f-a)/b$。
- 等待时间：在就绪队列中等待的累计时间。没有 I/O 阻塞的单段 CPU 模型中等于 $f-a-b$；有阻塞时还要扣除阻塞时间。
- 吞吐量：单位时间内完成的任务数；CPU 利用率：CPU 忙碌时间占观察时间的比例。

**最短剩余时间优先（SRTF）**是 SJF 的抢占版本。新任务就绪时，比较剩余服务时间。例如 A 在时刻 0 到达，需要 8 个时间单位；B 在时刻 1 到达，需要 2 个。SRTF 先运行 A 一个单位，再运行 B 至时刻 3，最后完成 A 至时刻 10。两者等待时间分别为 2 和 0。

**高响应比优先（HRRN）**在每次非抢占调度时选择下面比值最大的任务：

$$R=\frac{W+S}{S}=1+\frac{W}{S}$$

$W$ 是已经等待的时间，$S$ 是预计服务时间。短任务起初容易获得较高比值，长任务也会随等待提高优先级。例如 A 等待 6、服务 3，响应比为 3；B 等待 8、服务 8，响应比为 2，此时选择 A。

结束、阻塞或主动让出时需要重新调度；抢占系统还可在时间片耗尽、高优先级任务就绪等时机调度。实时调度常见**最早截止期限优先（EDF）**和按周期确定固定优先级的**速率单调调度（RM）**，能否按期完成还取决于执行时间和总负载。

多核调度兼顾负载均衡与处理机亲和性：迁移能分担忙核负载，也可能失去原核缓存。高优先级线程等待低优先级线程持有的锁时，还可能发生**优先级反转**，可用优先级继承缩短持锁线程受到的额外阻碍。

## 第四章：进程同步与互斥

本章讨论并发执行中的共享数据保护、信号量机制与死锁处理。

### 第一部分：并发访问冲突——为什么需要同步？

同一进程的线程共享地址空间，可以直接访问共同的数据。多个线程并发读写同一变量时，如果不加以协调，执行结果的正确性就会受到指令交错顺序的影响。

下面以游戏服务器中共享血量的更新为例说明这一过程。

#### 1. 共享变量的并发更新

**场景：** 假设游戏服务器内存里有一个共享变量 `Boss_HP = 1000`（Boss 的血量）。
现在，玩家 A（线程 A）和玩家 B（线程 B）同时放了一个技能，各自对 Boss 造成了 100 点伤害。
理论上，Boss 最终的血量应该是 `1000 - 100 - 100 = 800`。

但在底层 CPU 看来，“扣血”这个动作绝不是一瞬间完成的，它在汇编语言级别被拆分成了**三个微观步骤**：

1. **Read（读）：** 把内存里的 `Boss_HP` (1000) 读进 CPU 的寄存器里。
2. **Sub（减）：** 在 CPU 寄存器里执行减法，算出来结果是 900。
3. **Write（写）：** 把寄存器里的 900 写回内存的 `Boss_HP` 地址。

由于线程 A 和线程 B 并发执行，硬件时钟中断可能在这三个步骤之间的任意时刻发生，触发调度器切换线程。

### 第二部分：临界资源与竞态条件

讨论共享数据的保护时，需要区分资源本身与访问资源的代码：

#### 1. 临界资源与临界区

- **① 临界资源：** 指的是一次仅允许一个进程（或线程）使用的共享资源。 *在刚才的例子里，内存里的变量 `Boss_HP` 就是临界资源。共享打印机、需要互斥更新的文件和全局帧缓冲区，也属于这类资源。*
- **② 临界区：** 指的是访问临界资源的那**一段代码**。 *在刚才的例子里，包含 Read、Sub、Write 这三步操作的几行 C++ 或 Python 代码，就叫临界区。*

**访问同一临界资源的临界区需要互斥执行。** 线程 A 进入前先获取锁，退出时释放锁；线程 B 要等锁可用后才能进入。使用阻塞式互斥锁时，获取失败的线程进入等待队列。

#### 2. 常见误区：共享内存并不会自动加锁

一个常见的误解是：“既然 `Boss_HP` 是临界资源，线程 A 读取它之后，该变量是否会被系统自动锁住，从而阻止线程 B 修改？”

**实际上，操作系统和硬件不会自动识别程序中的临界资源并替它加锁。**

在 CPU 和内存硬件层面，并不存在“Boss 血量”这样的业务语义，`Boss_HP` 只是内存中的一个普通地址（如 `0x7FFF1A2B`）。如果代码中没有显式加锁，当线程 A 读完该地址后发生时钟中断，切换到的线程 B 可以直接读写同一内存地址，不会受到硬件或操作系统的自动阻拦。

硬件不自动对每次内存访问加锁的原因主要有两点：

1. **性能开销：** 内存包含数十亿个地址单元，若每次普通访存指令都伴随锁状态的检查与维护，访存性能将大幅下降。
2. **语义边界未知：** 硬件无法得知哪几条指令在业务逻辑上构成一个“不可分割的整体”。在 CPU 看来，`Read`、`Sub`、`Write` 只是三条独立的普通指令。

因此，**必须由程序员通过互斥锁或信号量显式标定临界区**，才能保证这三步操作的互斥执行。

#### 3. 并发更新丢失的时间线推演

假设未加任何同步锁，初始内存中 `Boss_HP = 1000`，扣血操作分为三步：① **Read**（从内存读入寄存器）→ ② **Sub**（寄存器内减 100）→ ③ **Write**（将寄存器结果写回内存）。由于每个线程在上下文切换时各自保存和恢复独立的寄存器状态，考虑如下交错执行顺序：

- **时刻 1：** 线程 A 开始运行，执行步骤 ①（Read），将当前内存值 `1000` 读入线程 A 的寄存器。
- **时刻 2：** 硬件时钟中断触发，线程 A 尚未执行减法即被剥夺 CPU，进入就绪态；其寄存器中的 `1000` 被保存在线程 A 的上下文中。
- **时刻 3：** 线程 B 获得 CPU 并执行步骤 ①（Read）。由于线程 A 尚未写回，内存中 `Boss_HP` 仍为 `1000`，线程 B 读入寄存器的值也是 `1000`。
- **时刻 4：** 线程 B 连续执行步骤 ②（Sub）和步骤 ③（Write），算出 `900` 并写回内存。此时内存中的 `Boss_HP` 更新为 `900`。
- **时刻 5：** 时钟中断再次发生，线程 B 被切走，线程 A 重新获得 CPU 并恢复先前保存的寄存器上下文（寄存器值为 `1000`）。
- **时刻 6：** 线程 A 从被中断的位置继续执行步骤 ②（Sub），用自己寄存器中的旧值 `1000` 减去 `100` 得到 `900`，随后执行步骤 ③（Write）将 `900` 写回内存。

![竞态交错的六个时刻：线程 A 和 B 都读到 1000，B 先写回 900，A 恢复旧寄存器后又写回 900，导致一次更新丢失](/images/notes/operating-system/race-condition-interleaving.svg)

最终，内存中的 `Boss_HP` 定格在 **900** 而非 800——线程 B 的更新被线程 A 基于旧值的写回操作覆盖了。

#### 4. 临界区协议与锁的实现

互斥访问由进入区、临界区、退出区和剩余区构成。协议需要满足互斥与进展要求：空闲时允许进入、已占用时排他、申请者等待有界。阻塞式方案还强调“让权等待”，避免拿不到资源时持续占用 CPU。

软件算法如 Peterson 算法用 `flag` 表示申请意愿、用 `turn` 处理双方同时申请。经典证明基于两参与者、原子读写和顺序一致内存模型；实际多核代码应使用语言提供的同步原语。

硬件的 Test-and-Set、Compare-and-Swap 等原子指令可以支撑锁。**自旋锁**反复检查，适合持锁时间很短且持锁者能继续运行的场景；**阻塞锁**使等待者睡眠，适合较长等待。单核屏蔽中断可保护部分内核临界操作，但不能独自阻止其他 CPU 核访问共享数据。

### 第三部分：信号量机制

Dijkstra 提出了信号量机制，用计数值和等待队列协调并发执行。

可以把信号量（通常用变量 `S` 表示）类比为**可用资源的“许可牌”数量**。
而 P 操作和 V 操作，是操作系统提供的两个**不可分割的原子操作（原语 Primitive）**。
原子性要求信号量的检查、计数更新和等待队列操作保持一致。实现时用同步措施保护这些步骤：单核内核可以通过暂时屏蔽中断保护关键操作，多核系统则需要原子指令和锁来协调各个 CPU 的访问。

两个操作分别负责申请和释放资源：

#### 1. P 操作（wait）：申请资源

线程进入临界区前，先执行 `P(S)` 申请许可：

- 先将信号量减 1：`S = S - 1`。
- 若减 1 后 `S >= 0`：表示仍有可用资源，线程继续进入临界区执行。
- 若减 1 后 `S < 0`：表示资源已耗尽（此时 `|S|` 的绝对值等于正在等待该资源的进程/线程数）。内核将该线程置为**阻塞态**，移入该信号量的等待队列并让出 CPU。

#### 2. V 操作（signal）：释放资源

线程退出临界区时，执行 `V(S)` 归还许可：

- 先将信号量加 1：`S = S + 1`。
- 若加 1 后 `S <= 0`：说明加 1 前 `S` 为负数，即等待队列中仍有阻塞等待的线程。内核从该信号量的等待队列中唤醒一个线程，将其移入**就绪队列**。
- 若加 1 后 `S > 0`：说明等待队列为空，无需唤醒其他线程。

#### 3. 用互斥信号量保护共享变量

针对前面的 `Boss_HP` 更新问题，可以设置一个初值为 1 的互斥信号量 `Mutex = 1`，将临界区代码包裹在 `P(Mutex)` 与 `V(Mutex)` 之间：

```c
P(Mutex);              // 进入区：申请互斥锁
reg = Read(Boss_HP);   // 临界区：读取血量
reg = reg - 100;       // 临界区：计算扣血
Write(Boss_HP, reg);   // 临界区：写回内存
V(Mutex);              // 退出区：释放互斥锁
```

线程 A 执行 `P(Mutex)` 进入临界区后，即使在 `Sub 100` 处发生时钟中断被切走，线程 B 调用 `P(Mutex)` 时也会因 `Mutex` 减为 `-1` 而进入阻塞队列等待。待线程 A 恢复运行、完成 `Write` 并调用 `V(Mutex)` 唤醒线程 B 后，线程 B 才能进入临界区并读取更新后的 `900` 继续计算。

![线程 A 持锁将共享血量从 1000 更新为 900，线程 B 获锁后再读 900 并更新为 800](/images/notes/operating-system/mutex-update-sequence.svg)

#### 4. 同步顺序：让 B 等 A 完成

互斥限制同时进入的数量，同步还表达先后顺序。若 B 必须等 A 生产数据，可设 `ready = 0`：A 写完后执行 `V(ready)`，B 在读取前执行 `P(ready)`。即使 A 先完成，信号量中的许可也会保留，供 B 之后取得。

#### 5. 生产者—消费者：容量与互斥

设缓冲区容量为 $N$，`empty = N` 表示空槽数，`full = 0` 表示已有产品数，`mutex = 1` 保护缓冲区和读写位置。使用阻塞信号量的伪代码如下：

```text
生产者：                       消费者：
生产一个产品                   P(full)
P(empty)                       P(mutex)
P(mutex)                       从缓冲区取出产品
把产品放入缓冲区               V(mutex)
V(mutex)                       V(empty)
V(full)                        消费产品
```

先等空槽或产品，再申请互斥锁。若消费者先持有 `mutex` 再等待 `full`，空缓冲区时生产者也无法入内放产品，双方就会卡住。生产和消费的耗时计算放在临界区外，可缩短持锁时间。

#### 6. 读者—写者与哲学家进餐

读者—写者允许多个读者共同读，但写者与任何其他访问者互斥。一个读者优先方案维护 `read_count`：用计数锁保护增减，首个读者取得写互斥锁，最后一个读者释放；写者独占该写互斥锁。持续到来的读者可能使写者饥饿，公平方案会增加等待队列或入口控制，让排在前面的写者也能进入。

哲学家进餐中，每人需要左右两支筷子。若所有人先拿左边再等右边，就形成循环等待。可将筷子统一编号，所有人先拿较小编号，再拿较大编号；也可用计数信号量限制同时尝试取筷子的人数为 $N-1$（$N\geq2$）。前者破坏资源申请环，后者避免所有人各占一支。无死锁与无饥饿是不同性质。

#### 7. 管程与条件变量

管程封装共享数据与操作，一次只允许一个线程执行受保护的操作。条件变量等待某个业务条件。常见的 Mesa 语义中，`wait` 原子地释放互斥锁并等待，被唤醒后重新取得锁；通知只使等待者有机会继续。

```text
lock(mutex)
while 缓冲区为空:
    not_empty.wait(mutex)
取出产品
not_full.signal()
unlock(mutex)
```

用 `while` 重新检查条件，因为唤醒后到重新持锁之间，其他线程可能已取走产品。条件变量的通知不累计许可，这与信号量不同。

### 第四部分：死锁

多个任务分别持有资源，又等待对方释放资源时，会陷入**死锁**。下面用两个任务申请厨具的过程说明这种等待关系。

场景中的角色对应如下：

- **CPU** = 唯一的厨师（你）。
- **进程/线程** = 两道正在并发烹饪的菜（任务 A 和任务 B）。
- **临界资源（且互斥）** = 厨房里只有**一口炒锅**（对应信号量 `Mutex_Wok = 1`）和**一把锅铲**（对应信号量 `Mutex_Spatula = 1`）。

为了做菜，你必须在代码里申请资源（拿牌子）：

- 任务 A（番茄炒蛋）： 它的代码逻辑是，必须先拿到炒锅，再拿锅铲，才能开炒。 `P(炒锅)` -> `P(锅铲)` -> 狂炒 -> `V(锅铲)` -> `V(炒锅)`
- **任务 B（红烧肉）：** 它的代码逻辑是，习惯先紧紧把锅铲握在手里准备好，再去端炒锅。 `P(锅铲)` -> `P(炒锅)` -> 狂炒 -> `V(炒锅)` -> `V(锅铲)`

**资源保持规则** 在这个例子中，时间片用完、切换去做另一道菜时，之前申请到的炒锅或锅铲仍由原任务持有，直到它执行相应的 `V` 操作释放。这里假设厨具只能由持有者主动归还，这对应资源的非抢占性。

#### 1. 资源申请的时间线

1. 时钟滴答，任务 A（番茄炒蛋）获得了 CPU 时间片，你成功执行了 `P(炒锅)`。此时炒锅被任务 A 锁死，你把炒锅端到了 A 的案板上。
2. 就在你准备去拿锅铲（还没来得及执行下一个 P 操作）的瞬间，**硬件时钟中断触发！**
3. CPU 被剥夺，调度器切换去执行**任务 B（红烧肉）**。
4. 你来到 B 的案板前，执行任务 B 的第一行代码，成功执行了 `P(锅铲)`。锅铲被任务 B 锁死，你把锅铲握在了手里。
5. 紧接着，任务 B 按照代码逻辑往下走，准备去端炒锅，于是它执行了 `P(炒锅)`。

#### 2. 四个必要条件

上述厨具争用场景对应死锁的四个必要条件。发生死锁时，这四个条件同时成立：

1. **互斥条件：** 炒锅和锅铲一次只供一个任务使用。
2. **请求和保持条件：** 任务 A 持有炒锅，在请求锅铲时继续保留炒锅。
3. **不剥夺条件：** 已分配的厨具由持有它的任务主动释放，其他任务无法强行取走。
4. **环路等待条件：** A 等待 B 的锅铲，B 等待 A 的炒锅，形成循环等待。

![任务 A 持有炒锅并等待锅铲，任务 B 持有锅铲并等待炒锅，资源申请与分配构成环](/images/notes/operating-system/deadlock-resource-cycle.svg)

死锁预防通过破坏其中至少一个必要条件，阻止这类循环等待形成。

#### 3. 如何对付死锁？（4.5 节后续）

处理死锁有三类策略：预防其形成、在分配资源时避免进入不安全状态，以及检测死锁后解除。

1. **死锁预防：破坏必要条件**
   
   - **原理：** 通过限制资源的申请或持有方式，破坏上述必要条件中的至少一个。
   - **代价：** 规矩太严，会导致厨房的炒菜效率（系统吞吐量）大幅降低。

2. **死锁避免：银行家算法**
   
   - **原理：** 在每次分配资源前先做一次试探性推演：假设把资源分配给当前申请的进程，系统是否仍处于**安全状态**（即仍存在至少一条使所有进程都能顺利运行完毕的序列）。若安全则予以分配；若会导致系统进入不安全状态，则暂不分配，让该进程等待。

   银行家算法分配资源前，要判断“给了之后系统还能不能找到一条安全退场路线”。

   你可以把系统想象成银行，进程是来借钱的客户。银行除了看柜台上现在有没有钱，还要判断借出这笔钱后，能否让所有客户按某个顺序顺利还款。

   手算时固定看四个量：

   - **最大需求**：每个进程最多可能要多少资源。
   - **已分配**：现在已经拿走多少资源。
   - **还需要**：还差多少资源才能完成。
   - **可用资源**：银行柜台上现在还剩多少资源。

   其中：

   ```text
   还需要 = 最大需求 - 已分配
   ```

   判断安全状态时，按这个流程走：

   1. 先看当前可用资源。
   2. 找一个“还需要”不超过当前可用资源的进程。
   3. 假装让它运行到结束。
   4. 它结束后，会归还自己已经占有的全部资源。
   5. 可用资源变多，再找下一个能完成的进程。
   6. 如果所有进程都能排进这个完成顺序，系统就是安全的。
   7. 如果找着找着卡住了，剩下进程谁都满足不了，系统就是不安全的。

   这个完成顺序就叫**安全序列**。

   资源请求题也一样。先假装把资源借给它，再重新做一次安全性检查。如果还能找到安全序列，就可以分配；如果找不到，就不能分配。

   所以银行家算法的答题句式通常是：

   ```text
   试分配后，重新计算可用资源与还需要资源。
   若存在安全序列，则该请求可以满足。
   若不存在安全序列，则该请求不能满足，因为会使系统进入不安全状态。
   ```

3. **死锁检测与解除：亡羊补牢**
   
   - **原理：** 系统检查资源的分配和等待关系。在这个每种厨具只有一件的例子中，等待图出现环路，就能确定发生了死锁。
   - **解除方式：** 可以终止选定的进程，回收其持有的资源，让其他进程继续执行。终止哪些进程，需要结合其运行进度、资源占用和重新执行的代价来选择。
     
---

#### 4. 银行家算法的请求步骤与例子

把资源数写成向量，比较均为逐分量比较。进程 $i$ 提出 `Request[i]` 后：

1. 检查 `Request[i] <= Need[i]`，超出最大声明需求则是非法请求。
2. 检查 `Request[i] <= Available`，当前数量不足则等待。
3. 试分配：`Available -= Request[i]`，`Allocation[i] += Request[i]`，`Need[i] -= Request[i]`。
4. 复制 `Work = Available`，寻找尚未完成且 `Need[i] <= Work` 的进程；模拟其完成，令 `Work += Allocation[i]`，重复寻找。
5. 所有进程都能完成则接受分配；否则恢复试分配前的数据，让请求等待。

例如只有一种资源，总数为 10：

| 进程 | 最大需求 Max | 已分配 Allocation | 尚需 Need |
| --- | ---: | ---: | ---: |
| P0 | 7 | 3 | 4 |
| P1 | 4 | 2 | 2 |
| P2 | 5 | 2 | 3 |

当前 `Available = 3`。可按 P1 → P0 → P2 完成，模拟可用量依次为 3 → 5 → 8 → 10。若 P0 再请求 2，试分配后可用量为 1，各进程尚需 2、2、3，都无法保证完成，应撤销试分配。

**不安全不等于已经死锁。** 不安全表示不能保证满足所有最大需求；进程可能不再申请最大额度而正常结束。检测死锁依据当前未满足请求，而非未来最大需求。每类资源只有一个实例时，资源等待环可判定死锁；有多个实例时，有环只是必要条件，还要检查是否有进程能完成并释放资源。

预防方法包括一次申请全部资源、申请失败时释放已有资源、统一申请顺序。检测后可以终止进程或回滚到可恢复状态。死锁是相互等待无法推进，饥饿是长期得不到机会，活锁则是持续重试或退让却没有实际进展。

## 第五章：存储器管理

前四章我们解决的是 CPU（算力）的分配问题。但 CPU 跑得再快，如果没有数据喂给它，它也就是个空转的加热器。内存就是 CPU 的“唯一饭碗”。

这一章讨论如何在有限的物理内存中安排多个进程，包括地址转换、空间分配、共享与保护。

理解进程使用的地址如何对应物理内存，是学习这些机制的起点。

---

### 第一部分：逻辑地址与物理地址

在 C/C++ 调试或反汇编中，经常能看到类似 `0x00400000` 这样的内存地址。

**地址转换：** 在这里讨论的虚拟内存环境中，程序使用的逻辑地址需要由操作系统和 CPU 配合转换为物理地址。

1. **逻辑地址与虚拟地址** 程序使用的地址与数据在物理内存中的位置可以分离。在分页系统中，进程使用虚拟地址，硬件按页表将其转换为物理地址。
   为了先理解地址转换，下面的重定位例子采用**从 `0` 开始编号的相对地址**，表示相对于程序起点的偏移。实际程序的代码和数据可以位于虚拟地址空间中的不同区域，起始地址由编译链接、装载方式与系统布局共同决定。

2. **物理地址** 这是处理器完成地址转换后用于访问物理地址空间的地址。在本章的内存示例中，它标识主存中的存储单元。实际系统的物理地址空间还可能包含映射给设备的区域。

**地址空间与保护：** 操作系统为进程建立地址映射和访问权限，硬件在访问内存时检查权限。程序越权访问内核或其他进程的内存时，会触发异常。

---

#### 从源代码到运行映像：编译、链接与装入

编译把源程序转为目标模块；链接解析模块间的符号引用并组合程序；装入为程序建立运行时的内存映像。静态链接在生成可执行文件时合入所需库代码；动态链接在装入时或运行时解析共享库引用，使多个进程可以共享只读代码页。

绝对装入使用事先确定的地址；可重定位装入在装入时修改有关地址；动态运行时装入把地址转换推迟到执行时。下一节分别说明后两者的重定位过程。

**覆盖**让不会同时执行的模块复用同一块内存，传统做法由程序或装入器安排；**交换**由操作系统将暂不运行的进程映像换出。请求分页进一步以页面为粒度按需调入，见第六章。

### 第二部分：重定位

沿用上面的相对地址例子，假设程序装在物理地址 `10000` 开始的位置。程序要访问相对地址 `100` 时，怎样找到对应的物理地址？

这就必须依靠一套**地址转换机制**，专业术语叫**重定位**。

它分为两种流派：

1. **静态重定位：** 程序装入内存时，装入程序按实际装入位置修改需要重定位的地址。例如，相对地址 `100` 加上装入基址 `10000` 后，得到地址 `10100`。
   
   - **位置依赖：** 地址在装入时已经确定。移动程序后，需要重新处理与装入位置相关的地址。

2. **动态重定位：** 程序执行时再把逻辑地址转换成物理地址。程序使用的地址与实际装入位置分离，转换机制负责建立对应关系。
   
   - **硬件支持：** **MMU**（内存管理单元）负责执行地址转换。用基址寄存器进行动态重定位时，它将逻辑地址与基址相加。
   
   - **运行原理：** 在这个基址重定位模型中，分派器切换进程时设置相应的基址寄存器。
     进程访问逻辑地址 `100`、基址为 `10000` 时，MMU 计算：**逻辑地址 (100) + 基址 (10000) = 物理地址 (10100)**，再访问对应位置。

**边界保护：** 基址寄存器确定起点，界限寄存器记录可访问范围。硬件先检查逻辑地址是否越界，通过检查后再与基址相加；越界访问触发异常。

### 第三部分：连续内存分配

连续分配要求一个进程占用一段连续的物理地址。先区分空间如何划分，再讨论从空闲区中选哪一块。

#### 1. 单一连续分配

内存划分为系统区和用户区，用户区一次只装一个用户程序。实现简单，但多余空间不能再交给另一个用户程序，无法支持多个用户程序同时驻留的多道运行方式。

例如用户区共 64MiB，程序只需 20MiB，剩余 44MiB 在这个模型中也不能装入另一个进程。这是已给定用户区内未被使用的空间，通常归为内部浪费。

#### 2. 固定分区分配

预先把用户区划成若干固定大小的分区，每个分区最多容纳一个进程。**分区大小相等**便于管理，但大小任务都用相同空间；**分区大小不等**则准备不同规格，以匹配不同需求。

若分区为 16MiB、32MiB、64MiB，20MiB 的程序放进 32MiB 分区后，余下 12MiB 仍属于这个分区，不能分给别的进程，形成**内部碎片**。80MiB 的程序即使面对总计 112MiB 的空闲分区，也放不进任何一个分区。可同时驻留的进程数受分区数量限制。

#### 3. 动态分区分配（可变分区）

分区随进程申请动态建立：需要多少空间，就从一个足够大的空闲区中划出相应大小，余下部分继续保持空闲。回收后再与相邻空闲区合并。它减少固定分区中的内部浪费，但会产生散落在已分配区之间的**外部碎片**。

操作系统可用空闲分区表或空闲链表记录空闲区的起始地址与长度。接下来的适应算法，解决的就是动态分区中“选哪个空闲区”的问题。

| 分配方式 | 用户区如何划分 | 主要空间问题 |
| --- | --- | --- |
| 单一连续 | 一个用户区，一次一个用户程序 | 剩余空间无法供另一进程使用 |
| 固定分区 | 预先划分，大小不变 | 分区内部空余；进程大小受单个分区限制 |
| 动态分区 | 按请求划分，回收时合并 | 分区之间产生外部碎片 |

![连续分配的三种方式与碎片位置](/images/notes/operating-system/contiguous-allocation-types.svg)

#### 4. 动态分区的空闲区选择

可以把空闲分区看作待分配的房间，把作业看作申请空间的进程。

假设现在有两个空闲区：

```text
F1 = 200KB
F2 = 60KB
```

作业依次到来：

```text
A = 30KB
B = 70KB
C = 50KB
```

##### 首次适应（First Fit）

首次适应的规矩是：从低地址开始找，遇到第一个装得下的空闲区就放进去。

它不追求最省，只追求“从前往后第一个能住就住”。

对于上面的例子：

```text
A 先看 F1，F1 能装，于是放入 F1，F1 剩 170KB。
B 再从头看，F1 剩 170KB 还能装，于是放入 F1，F1 剩 100KB。
C 再从头看，F1 剩 100KB 还能装，于是放入 F1，F1 剩 50KB。
F2 仍然是 60KB。
```

首次适应通常速度快，因为它不用把所有空闲区都看完。

但它容易把低地址区域切得很碎，前面会出现一堆小碎片。

##### 最佳适应（Best Fit）

最佳适应的规矩是：找所有能装下它的空闲区里，最小的那个。

它的思路是：尽量保留大块空闲区，先用大小最接近的空闲区满足当前请求。

对于上面的例子：

```text
A = 30KB：F1 能装，F2 也能装，选更小的 F2，F2 剩 30KB。
B = 70KB：F2 剩 30KB 装不下，只能放入 F1，F1 剩 130KB。
C = 50KB：F1 剩 130KB 能装，F2 剩 30KB 装不下，放入 F1，F1 剩 80KB。
```

最佳适应看起来省空间，但它经常制造特别小、特别尴尬的碎片。比如剩下 1KB、2KB 的空洞，看着还在，实际很难再用。

##### 最坏适应（Worst Fit）

最坏适应每次挑最大的空闲区。

它的想法是：切也从最大的地方切，剩下的碎片至少还比较大，不至于马上变成废料。

但它也有问题：大空闲区会被很快切小，后面真正的大作业来了，可能反而没地方放。

![F1 为 200KB、F2 为 60KB，A、B、C 依次分配时首次、最佳与最坏适应的布局](/images/notes/operating-system/memory-allocation-fit.svg)

##### 分配题的推演步骤

不要只写“能放”或“不能放”。考试要看过程。

标准写法：

```text
当前空闲区：F1=200KB, F2=60KB
作业 A=30KB，按某算法选择某分区，剩余多少。
作业 B=70KB，按某算法选择某分区，剩余多少。
作业 C=50KB，按某算法选择某分区，剩余多少。
```

本质上这类题和银行家算法很像：别凭感觉，按规则一步步更新状态。

##### 邻近适应（Next Fit）与回收合并

邻近适应也叫循环首次适应：从上次查找结束的位置继续向后找，遇到足够大的空闲区即分配，走到末尾再回到开头。它减少了每次从低地址重新搜索的重复工作，也可能较快切碎高地址的大空闲区。

首次适应按地址顺序搜索；最佳、最坏适应按大小挑选，搜索成本取决于空闲表或索引的组织方式。分配后要更新空闲区起点与长度；整块用完则删除相应记录。

回收时有四种情况：两侧都不空闲，新增空闲记录；仅与前侧相邻，向前合并；仅与后侧相邻，向后合并；两侧都相邻，合为一个大空闲区。例如 `[100,140)` 和 `[160,200)` 已空闲，再释放 `[140,160)` 后，得到 `[100,200)`。这些都是相邻合并，未移动任何在用数据。

**紧凑**才会移动已分配区，把分散空洞集中起来，需要可重定位支持，并协调正在访问这些内存的 CPU 和设备。相邻合并与紧凑是不同操作。

### 第四部分：内存碎片与分页

沿用上一节的**动态分区分配**：
程序 A 需要 10MB，就在内存里找一块连续的 10MB 塞进去；程序 B 需要 20MB，紧挨着 A 塞进去。

动态分区会在内存反复分配和回收后留下分散的空闲区，这就是**外部碎片**。

想象一下：

1. 你的物理内存有 100MB。

2. 你依次打开了三个程序：A (20MB), B (30MB), C (20MB)。此时内存还剩最后连续的 30MB 空间。

3. 现在，你关掉了中间的程序 B。B 占用的 30MB 被释放了。

4. 此时，物理内存里总共有两块空闲地盘：中间的 30MB，和最后的 30MB。**总空闲内存是 60MB。**

5. 此时你想打开一个 40MB 的 3A 大作。

6. **分配失败：** 总空闲容量有 60MB，但没有一块**连续的** 40MB 空间，因此无法满足这次申请。

这些分散的空闲区形成了**外部碎片**：它们各自能满足较小的申请，却无法合并成一块连续大空间。紧凑（Compaction）操作可以通过移动已分配区域来合并空闲空间，但数据搬移和地址调整的开销较大。

为避免外部碎片和频繁搬移内存，操作系统引入了**分页存储管理（Paging）**：将物理内存划分为固定大小的块（称为**页框 / 物理块**，如 4KB），同时将进程的逻辑地址空间也划分为同样大小的**页面（Page）**。进程运行时，各个页面可以离散地装入任意空闲的物理页框中，无需占用一整块连续的物理内存。

- **定长页框与内部碎片：** 例如 10KB 的程序，分配 3 个 4KB 的页框（共 12KB）。这种方式消除了外部碎片，但最后一个页框会剩余 2KB 未被利用的空间，称为**内部碎片**（若各进程末页余量近似均匀分布，平均浪费约半页）。
- **页表（Page Table）：** 由于进程的各个页面离散存放在物理内存中，操作系统需要为每个进程维护一张**页表**，记录“逻辑页号 → 物理块号”的映射关系。
![逻辑页离散映射到物理页框，10KB 进程占用三个 4KB 页框，最后页框保留 2KB 内部碎片](/images/notes/operating-system/paging-page-frames.svg)

- **页表空间开销计算示例** 假设某 32 位进程的虚拟地址空间为 **4GiB**（$2^{32}\text{ B}$），页面大小为 **4KiB**（$2^{12}\text{ B}$），每个页表项（PTE）占 **4B**。这里用 GiB、KiB、MiB 表示二进制容量单位。
  - 页表项数量 $= 2^{32} / 2^{12} = 2^{20} = 1{,}048{,}576 \approx 104.86\text{ 万项}$。
  - 单进程页表大小 $= 2^{20} \times 4\text{ B} = 2^{22}\text{ B} = 4\text{ MiB}$。
  - 若用单级连续页表覆盖整个虚拟地址空间，一个进程的页表就需要 $4\text{ MiB}$ 的连续物理内存。多级页表可以按需分配下级页表，减少稀疏地址空间的页表开销。

### 第五部分：为什么还要有“分段”？
**分页主要服务于固定粒度的内存管理，分段反映程序的逻辑组织**。

**分页的局限：** 分页按固定大小（如 4KB）划分空间，不感知程序的逻辑结构。

- 一段完整的功能模块或核心控制逻辑可能恰好跨在两个页面的边界上，代码区与数据区在页粒度上也不如按逻辑模块划分那样直观，不利于按逻辑模块进行**共享**和**权限保护**。

**解决原理：分段。** 分段是按照程序员的逻辑意图来切分内存。比如：

- **段 0：** 你的主程序代码区。

- **段 1：** 全局变量数据区。

- **段 2：** 函数调用的栈区。

**区别与联系：**

1. **页：** 是固定大小的地址空间划分单位，虚拟页与物理页框大小相同。分页方便离散分配并消除进程整体连续分配的外部碎片，末页仍可能有内部碎片。

2. **段：** 是逻辑单位。长度不固定，对用户可见。目的是方便编程、方便共享和保护。

**账本升级：段表** 段表和页表很像，但多了一个维度。页表只记“物理块号”，而段表要记“**这段的起点**”和“**这段的长度**”。硬件根据段界限和权限检查访问。Unix 系统中的 `Segmentation Fault` 泛指一类非法内存访问结果，也可能来自未映射页面或权限错误，并不专指传统分段模型中的段越界。

### 第六部分：段页式存储

**段页式管理**结合了两种划分方式：先按逻辑分段，再把每个段划分为固定大小的页。

**微观物理过程：**

1. 先按照逻辑，把程序分成一个个**段**（代码段、数据段）。

2. 在每一个段内部，再强行切成一个个 4KB 的**页**。

3. **地址转换流程：** CPU 要找一个数据，先去查**段表**，找到该段对应的**页表**起始地址；再去查**页表**，找到具体的**物理块号**；最后加上偏移量拿到数据。

**代价：** 在段表和单级页表都存于内存、地址转换未命中缓存的这个模型中，读取数据要先查段表、再查页表，最后访问数据，共三次内存访问。TLB 可以缓存地址转换结果，减少查表开销。

### 第七部分：盲点整合——碎片与双表关系

- **固定分区、动态分区与纯分段：** 固定分区主要产生内部碎片；动态分区和纯分段按可变长度分配连续区，可能产生外部碎片。碎片类型取决于分配单位，不能仅以“是否连续”判断。

- **引入页表（分页机制）之后：** 物理内存按固定大小划分为页框，例如 4KB。进程的各页可以放入不连续的页框，页表记录它们的对应关系。分配这些页框时，无需寻找能容纳整个进程的连续空闲区。

- **代价：** 代价就是**内部碎片**。程序的大小未必是 4KB 的整数倍。比如程序要 13KB，系统只能给它分配 4 个格子（16KB）。最后一个格子里没装满的 3KB，就被浪费了。由于这 3KB 位于已分配给该进程的页框内部，因此称为内部碎片。

段表和页表是独立的数据结构，还是组合使用的？

**段表和页表都存储地址映射信息，具体表项由内存管理方式决定：**

1. **在纯分页系统里：** 只有页表。页表记录虚拟页对应的 `物理块号`，以及存在位、权限等状态。

2. **在纯分段系统里：** 只有段表。段表这个数组里存的是：`这一段在物理内存的真实起点地址` + `这一段的长度`。

3. **在段页式系统里：段表与页表分级配合。**
   
   - 在这个系统里，段表里存的**不再是**物理内存的起点地址了！
   
   - 段表里存的是：**这个段所专属的那个“页表”的物理地址！**
   
   - 也就是说：**段表指向页表，页表才指向真正的物理内存。** 它们在物理上是好几块分开的数组，但在逻辑上被一根无形的链条锁在了一起。

### 第八部分：地址转换全流程（宏观与微观）

下面按执行顺序说明操作系统建立映射、MMU 完成地址转换的过程。

下面采用教材中的段页式模型，假设一个进程包含核心代码段，页大小为 4096 字节（4KiB）。这个示例用于理解两级映射；常见 x86-64 系统通常使用平坦地址空间和多级页表，程序文件中的代码段不等于这里的硬件段表项。

#### 1. 第一阶段：建立映射表（由操作系统内核完成）

1. **逻辑切分：** 当你双击运行这个程序，操作系统首先看它的文件头，发现它分为代码段（段 0）、数据段（段 1）等。

2. **页面划分：** 操作系统将“代码段”按 4KB 划分为若干逻辑页（页 0、页 1……）。

3. **塞入内存：** 操作系统去物理内存里找空闲的格子（比如找到了物理块 105, 物理块 208）。把代码段的第一页塞进 105，第二页塞进 208。

4. **建立段表与页表：**
   
   - OS 在内存里创建一张**页表**，记录：页 0 → 块 105，页 1 → 块 208。
   
   - OS 在内存里创建一张**段表**，在第 0 行（代表段 0）写下：**刚才那张页表的物理起始地址**，以及这段代码的总长度（防越界）。

5. **移交权力：** OS 把这张段表的起始地址，存进这个进程的 **PCB** 里。然后把 CPU 交给这个进程。

#### 2. 第二阶段：运行时硬件寻址（由 MMU 硬件自动完成）

现在，CPU 正在执行代码，突然遇到一条指令：`读取 段0，第 5000 字节 位置的数据`。（这就是**逻辑地址**：段号=0，段内偏移=5000）。

1. **启动硬件：** 发生进程切换时，OS 已经提前把 PCB 里的“段表起始地址”塞进了 CPU 内部的一个硬件寄存器（段表寄存器）。

2. **查段表（第一次访问内存）：** MMU 硬件根据寄存器，直接去内存里找到段表的第 0 行。
   
   - MMU 检查段号是否合法、偏移 5000 是否小于段长、访问权限是否允许；失败则触发异常，由内核处理。
   
   - 如果没有越界，MMU 从段表里拿到了**属于段 0 的那张页表的起始地址**。

3. **算页号：** MMU 硬件在内部极速计算：5000 字节到底在第几页？（5000 / 4096 = 1...余 904）。所以它在**页 1**，页内偏移是 **904**。

4. **查页表（第二次访问内存）：** MMU 顺着刚才拿到的页表地址，去查页表的第 1 行。它发现，页 1 对应的真实物理块号是 **208**。

5. **拼装真实地址：** MMU 把 物理块号 208 转换成真实物理地址（208 * 4096 = 851968），然后加上刚才的页内偏移 904。
   
   - **最终绝对物理地址 = 851968 + 904 = 852872。**

6. **拿到数据（第三次访问内存）：** CPU 根据 852872 这个真正的物理地址，去内存条里把数据读出来，放进寄存器参与运算。

![段内偏移 5000 分解为页号 1 和偏移 904，查段表和页表得到物理块 208，拼成地址 852872](/images/notes/operating-system/segmented-paging-lookup.svg)

#### 3. 快表（TLB）加速

在上面的段页式转换模型中，一次数据访问包含查段表、查页表和读取数据三个步骤。地址转换结果可以缓存起来，减少重复查表。

所以，CPU 内部专门准备了一块极速的 **TLB 快表**。

它可以理解成地址转换的“小抄本”：页表和段表是完整账本，放在内存里，查起来慢；TLB 是硬件缓存，放在 CPU 附近，只记录最近用过的地址转换结果，查起来极快。

MMU 完成地址转换，得到 `段0，页1` 对应 `物理块208` 后，将映射结果存入 TLB，供后续访问查询。

下一秒钟，当你代码里的 `for` 循环要读取 5004 字节的数据时，MMU 直接在 TLB 里瞬间查到它依然在物理块 208，**直接省略掉查段表和查页表的过程**，直接去内存拿数据！

#### 4. 单纯分页与多级页表的计算

设虚拟地址为 $A$、页大小为 $L$，页号 $p=\lfloor A/L\rfloor$，页内偏移 $d=A\bmod L$。查询页表得到页框号 $f$ 后，物理地址为 $fL+d$。例如 $A=12345$、$L=4096$，得到页号 3、偏移 57；若页 3 映射到页框 20，则物理地址是 $81977$。

32 位地址、4KiB 页面和 4 字节页表项的教学模型中，一个页表页可放 1024 项。因此可把地址拆为 **10 位页目录索引 + 10 位页表索引 + 12 位偏移**。只给使用到的区域分配二级页表，可节省稀疏地址空间的页表内存；每多一级，未命中 TLB 时的查表访问也会增加。

在单级页表、无缺页、无数据缓存、先查 TLB 的简化模型中，设 TLB 查询时间为 $t$、内存访问时间为 $m$、命中率为 $h$：

$$EAT=h(t+m)+(1-h)(t+2m)$$

例如 $t=10\text{ ns}$、$m=100\text{ ns}$、$h=0.9$，平均为 120ns。页表还有存在位、读写执行权限、访问位和修改位；两个进程可将各自虚拟页映射到同一物理页框实现共享，并分别限制访问权限。

## 第六章：虚拟存储器

### 第一部分：虚拟内存与请求分页

“按需加载”，在专业术语里叫**请求分页**。

**基本思路：** 基于程序的局部性原理，进程在一段时间内通常只访问少部分代码和数据。因此操作系统无需在启动时将进程的全部页面装入物理内存，而是为其提供完整的虚拟地址空间，仅在页面实际被访问时才将其调入物理内存。

- **局部性直觉：** 就像阅读一本厚书时，桌面上不需要同时摊开每一页，只需摆放当前正在阅读的几页；读到后续章节时，再把新页翻开替换旧页。
- **核心机制——缺页中断：** 当 CPU 访问的逻辑页尚未装入物理内存（页表项中的有效位/存在位为 0）时，MMU 触发**缺页异常（Page Fault）**，陷入操作系统内核，由内核从外存将该页调入内存并更新页表。

#### 局部性、页表项与缺页处理

**时间局部性**是刚访问的内容可能很快再次访问；**空间局部性**是相邻地址可能相继被访问。请求分页据此允许程序多次、部分装入，在有限物理内存上提供较大的虚拟地址空间。

| 页表信息 | 用途 |
| --- | --- |
| 页框号与存在位 | 页面驻留时定位物理页框 |
| 访问位 R | 记录近期是否访问，供置换策略参考 |
| 修改位 M（脏位） | 记录内容是否改变，判断回收前是否需要保存 |
| 权限位 | 检查读、写、执行及用户态访问权限 |

一次合法但尚未驻留的访问，处理顺序如下：

1. 硬件触发缺页异常，内核检查地址是否属于合法映射、权限是否允许。非法地址或权限错误进入错误处理。
2. 找空闲页框；不足时选择牺牲页。修改过且需要保留的内容先写回，已有可靠后备副本的干净页可以直接回收。
3. 从可执行文件、映射文件或交换区读入所需页；首次访问匿名页也可能直接分配清零页，无需磁盘读取。
4. 更新页表及相关 TLB 项；若曾等待 I/O，进程重新进入就绪队列。
5. 恢复执行时，重新执行引发缺页的指令。

**TLB 未命中只说明缓存中没有翻译结果。** 查页表发现页面驻留，仍可完成访问；缺页意味着需要内核介入处理页面或权限状态。

### 第二部分：页面置换算法

当发生缺页中断且分配给该进程的物理页框已满时，操作系统需要选择一个可回收的驻留页，必要时保存修改内容，再腾出页框装入新页。

页面置换算法的核心目标是：**尽量选择未来不再访问或最晚被访问的页面换出，从而降低缺页率。**

#### 1. 手动推演模板（3 个页框，访问序列：7 -> 0 -> 1 -> 2 -> 0 -> 3）

- 初始装入：
  - 读 7，缺页，内存：[7, 空, 空]
  - 读 0，缺页，内存：[7, 0, 空]
  - 读 1，缺页，内存：[7, 0, 1]

- 读 2，缺页且内存已满：
  - 若按 FIFO（先进先出），踢掉最先进入的 7，内存变为：[2, 0, 1]

- 紧接着读 0：
  - 0 在内存中，属于命中

- 最后读 3：
  - 若按 LRU（最近最久未使用），此时在 [2, 0, 1] 中，1 距离上次访问最久，踢掉 1

![三个页框独立执行 FIFO 与 LRU，访问序列 7、0、1、2、0、3，最后分别换出 0 与 1](/images/notes/operating-system/fifo-lru-page-replacement.svg)

#### 2. 关键陷阱：LRU 不等于 LFU

- **LRU：** 只看“最近有没有被访问过”，看的是时间。
- **LFU：** 看的是累计访问次数（频率）。

两者会在很多场景得出不同结论，考场和面试经常把这两个概念混在一起挖坑。

#### 3. 常见算法族谱（提炼）

- **OPT（最佳置换）：** 需要预知未来，现实不可实现，作为给定访问序列与页框数下缺页次数的理论下界。
- **FIFO：** 实现简单，但可能踢掉马上要用的页面。
- **LRU：** 贴近局部性原理，但精确实现开销高。
- **Clock：** 用访问位和循环指针给近期访问过的页面第二次机会。
- **NRU：** 按访问位和修改位分类后选择牺牲页，与 Clock 不是同一个算法。

#### 4. Clock 的具体过程与 Belady 异常

简单 Clock 将页框连成环。访问页面时置 `R=1`；置换时从指针位置检查：`R=0` 就换出，`R=1` 就清零并向前移动，直到找到牺牲页。换入页面置 `R=1`，指针继续移向下一页框。

例如三页框为 `[A:1, B:0, C:1]`，指针指向 A。缺页时先把 A 的访问位清零，再遇到 B 的 0，将 B 替换。增强型 Clock 还考虑修改位，优先寻找近期未访问且不需要写回的页面。NRU 通常依 `(R,M)` 分为 `(0,0)、(0,1)、(1,0)、(1,1)` 四类，从最低的非空类别选择，并周期性清除访问位。

FIFO 可能出现**Belady 异常**：页框增加，缺页反而更多。访问序列 `1,2,3,4,1,2,5,1,2,3,4,5`，FIFO 使用 3 个页框缺页 9 次，4 个页框缺页 10 次。LRU 和 OPT 具有栈性质，增加页框不会出现这种缺页数反增。

### 第三部分：抖动与工作集

#### 1. 什么是“抖动”（Thrashing）？

如果分配给进程的物理页框过少，刚换出的页面很快又被访问，就会导致缺页中断高频触发。

- **频繁换页：** 例如一个循环体跨越了 4 个页面，但系统只给该进程分配了 2 个物理页框。执行过程中每推进几条指令就会触发缺页中断，刚换入的页面尚未充分利用又被换出。
- **宏观表现：** 系统大部分时间都消耗在磁盘与内存之间的页面换入换出（I/O 等待）上，CPU 真正执行用户指令的时间占比极低。

在操作系统中，这种页面频繁换入换出、进程大量时间用于等待调页，从而导致 CPU 利用率与系统吞吐量急剧下降的现象称为**抖动（颠簸）**。

#### 2. 解决方案：工作集（Working Set）

发生抖动的直接原因是：**分配给进程的物理页框数（驻留集）小于该进程当前阶段高频访问的页面数。** 为定量刻画这一需求，Denning 提出了**工作集模型**：

- **工作集定义：** 在某时刻 $t$ 往前的一段固定时间窗口 $\Delta$ 内，进程实际访问过的页面集合。
  - 例如在某阶段的时间窗口内，程序反复访问页面 `{1, 2, 3}`，则该阶段的工作集为 `{1, 2, 3}`，至少需要 3 个物理页框。
  - 进入下一阶段后，工作集可能平滑转移为 `{4, 5, 6, 7}`，此时需要 4 个物理页框。
- **驻留集与工作集的关系** 操作系统分配给进程的物理页框集合称为**驻留集**。按工作集模型分配内存时，驻留集应能容纳当前工作集中的页面，即
  $$\text{驻留集大小} \ge \text{工作集大小}$$
  若驻留集长期无法容纳当前频繁访问的页面，就容易频繁换页，甚至发生抖动。

#### 3. 通过挂起减少内存压力

物理内存只有 100 个页框，而 10 个程序的工作集共需要 120 个页框，内存就难以同时容纳它们近期频繁使用的页面。程序争用页框会增加换页，挤占实际执行任务的时间。

**中级调度**（挂起）可以减少同时驻留内存的进程数。

调度器选择部分进程挂起，回收其占用的页框，让剩余进程的工作集能够驻留内存，减少反复换页。

### 第四部分：页框分配与请求分页的代价

**分配策略**决定给每个进程多少页框，可固定分配或动态调整；**置换范围**决定从哪里选牺牲页，局部置换只选本进程的页，全局置换还可回收其他进程的页。固定分配通常配合局部置换，动态分配可根据工作集或缺页率调整。

缺页率过高时增加页框，过低时回收部分页框；若总工作集超过可用物理内存，仅在进程之间搬移页框难以缓解抖动，需要降低多道程序度。调页还可采用预调页，但预取过多会读入尚不需要的数据。

设正常访问代价为 $T_m$，发生缺页后完成这次访问的总代价为 $T_f$，缺页概率为 $p$：

$$EAT=(1-p)T_m+pT_f$$

若 $T_m=100\text{ ns}$、$T_f=10\text{ ms}$、$p=10^{-6}$，平均约为 110ns。即使缺页比例很低，磁盘调页也会影响延迟。

**写时复制（COW）**让多个进程先共享只读物理页，发生写访问时再复制并调整映射；**内存映射文件（mmap）**把文件区间映射到虚拟地址空间，按页装入，更新是否写回文件取决于共享或私有映射。它们都建立在地址映射、权限检查和异常处理之上。

## 第七章：输入输出系统

前面几章我们一直在讲 CPU、内存、进程和页面。可是计算机真正和现实世界发生关系，靠的是输入输出设备：键盘、鼠标、显示器、打印机、网卡、磁盘。

这章要解决 CPU 与外设之间的矛盾。

**CPU 太快，外设太慢；外设种类太多，程序又不应该知道每个设备的脾气。**

所以操作系统必须先当一个翻译官和调度员：上层程序只说“我要输入”“我要输出”“我要打印”，操作系统负责把这句话翻译成具体设备能听懂的动作。

---

### 第一部分：输入输出的功能

你可以把 CPU 想象成一个反应极快的厨师，而外设像一堆性格完全不同的供应商：

- 键盘一次只送来一个字符。
- 磁盘一次适合搬一整块数据。
- 打印机慢得像排队盖章。
- 网卡的数据可能突然成批涌进来。

如果让用户程序直接和这些设备打交道，写一个保存文件的功能，还得处理控制器命令、磁头寻道和缓冲区排队等细节。设备接口的差异会增加应用开发与维护的负担。

所以操作系统在中间加了一层抽象：

1. 用户程序只面对统一接口，比如读、写、打开、关闭。
2. 操作系统把请求交给设备驱动程序。
3. 设备驱动程序再去指挥具体硬件。

这就是输入输出系统的第一条主线：**把复杂硬件包装成统一、稳定、好用的接口。**

---

### 第二部分：设备控制器与设备驱动程序

#### 1. 设备控制器：硬件世界的前台

CPU 不会直接伸手去拧磁盘马达，也不会直接控制打印机喷头。它面对的是设备控制器。

设备控制器就像每个外设前面的“前台窗口”。CPU 把命令交给前台，前台再去指挥真正的设备。

设备控制器里通常有三类寄存器：

- **数据寄存器**：存放要输入或输出的数据。
- **状态寄存器**：告诉 CPU 设备现在忙不忙、有没有出错、数据准备好了没有。
- **控制寄存器**：CPU 往这里写命令，比如开始读、开始写、复位设备。

所以，输入输出是 CPU 对控制器的寄存器读写。

#### 2. 设备驱动程序：操作系统里的专职翻译

不同设备控制器的命令格式不同。磁盘有磁盘的说法，打印机有打印机的说法，网卡有网卡的说法。

如果操作系统内核每次都亲自记住所有设备细节，它会臃肿到无法维护。

于是就有了设备驱动程序。

驱动程序的作用是：

- 接收操作系统发来的通用请求。
- 把通用请求翻译成具体设备命令。
- 处理中断和错误。
- 把结果再交还给操作系统。

你可以把它理解为“专业设备翻译”。操作系统内核发出通用请求：“读取该数据块”，磁盘驱动程序负责把这句话变成磁盘控制器能执行的一组命令。

#### 3. 设备独立性

设备独立性的意思是：应用程序不应该依赖具体设备。

比如你写：

```text
打印这份文档
```

程序不应该关心现在接的是惠普打印机、佳能打印机，还是虚拟打印机。只要操作系统提供统一接口，底层换设备时，上层程序尽量不用改。

即通过抽象层屏蔽底层物理设备的差异：底层硬件可以替换，上层应用接口保持稳定。

---

#### 4. I/O 软件层次与设备分配

请求沿着“用户程序与库 → 设备独立软件 → 设备驱动 → 控制器与设备”传递，完成后由中断处理和唤醒机制反馈。设备独立层负责命名、权限、缓冲、分配与统一错误处理，驱动负责具体设备协议。

块设备按可寻址的数据块访问，适合磁盘等存储；字符设备按字节流或事件提供接口。独占设备需要申请、排队和释放，共享设备可交错服务多个请求。教材常用系统设备表 SDT、设备控制表 DCT，以及控制器表 COCT、通道表 CHCT 描述设备及其连接和占用关系。分配时还需保证所经控制器与通道可用。

### 第三部分：输入输出控制方式

这一节是考试爱考概念区分的地方。你只要抓住一个问题：**CPU 到底要不要一直守着设备？**

#### 1. 程序直接控制（轮询方式）

最原始的方法是：CPU 不停地问设备控制器：

```text
好了没？
好了没？
好了没？
```

如果设备还没准备好，CPU 就继续原地等。

这叫程序直接控制。

**优点**：简单。

**缺点**：CPU 利用率低。外设速度远慢于 CPU，轮询期间 CPU 处于忙等状态，无法执行其他任务。

#### 2. 中断控制：外设好了再敲门

更聪明的方法是：CPU 发出输入输出命令后，不再傻等，而是去执行别的进程。

等设备完成任务后，它通过硬件中断告诉 CPU：

```text
我好了，你来处理一下。
```

这就是中断控制。

它解决了 CPU 空等的问题，是操作系统并发能力的重要基础。

但它也有代价：如果每传一个字节就中断一次，CPU 会被频繁打断，像刚坐下写作业就被叫起来开门，效率仍然不高。

#### 3. 直接内存访问：搬运工绕开 CPU

如果要从磁盘读一大块数据，让 CPU 逐次从设备读取数据再写入内存，会占用较多处理器时间。CPU 像个忙着来回搬货的搬运工，能用于其他任务的时间就少了。

直接内存访问的思路是：让专门的控制器负责在设备和内存之间批量搬数据。

CPU 只需要一开始交代清楚：

```text
从哪里读，读多少，放到内存哪里。
```

然后控制器自己搬。搬完之后，再用一次中断通知 CPU。

通过将批量数据搬运交给 DMA 控制器，CPU 只需下达传输指令并在传输结束时处理一次中断即可。

#### 4. 通道方式：更专业的搬运队长

在大型系统里，还可以有更强的输入输出处理部件。它不只是搬数据，还能执行一小段输入输出程序，自己安排多个设备的输入输出。

这叫通道方式。

你可以把它理解为：直接内存访问只是一个搬运工，通道则是一个小队长，能看懂任务清单，能组织一批搬运工干活。

![轮询、中断、DMA 与通道四种 I/O 控制的数据路径和 CPU 参与方式](/images/notes/operating-system/io-control-modes.svg)

考试记忆顺序：

```text
程序直接控制 -> 中断控制 -> 直接内存访问 -> 通道方式
```

方向是：CPU 越来越少被琐碎输入输出拖住，设备系统越来越独立。

---

### 第四部分：缓冲技术

#### 1. 为什么要缓冲？

缓冲区就是内存里专门开出来的一块中转区。

它解决的是速度不匹配问题。

比如你看视频：

- 网卡一阵一阵地收数据。
- 播放器希望稳定地读数据。

如果没有缓冲，网络稍微抖一下，画面就卡一下。

有了缓冲，操作系统先把数据放进内存中的缓冲区，应用程序再从缓冲区平稳读取。

缓冲区就像厨房备菜台。供应商送菜不是匀速来的，但厨师做菜希望手边一直有菜。备菜台越合理，厨房越不容易乱。

#### 2. 单缓冲

单缓冲就是只有一个中转托盘。

设备往托盘里放数据，CPU 或进程从托盘里拿数据。

放和拿经常互相等待。设备正在往托盘里放东西时，进程可能没法拿；进程正在拿时，设备可能没法继续放。

#### 3. 双缓冲

双缓冲准备两个托盘。

一个托盘给设备写，另一个托盘给进程读。等双方完成后交换。

这就像两个快递箱轮流使用：快递员往 A 箱塞包裹时，你从 B 箱取包裹；下一轮反过来。

双缓冲比单缓冲更能让设备和 CPU 并行工作。

![单缓冲交替填充和取走，双缓冲让设备写入一块时进程读取另一块，完成后交换角色](/images/notes/operating-system/single-double-buffer.svg)

#### 4. 循环缓冲与缓冲池

如果数据流更连续，就可以准备多个缓冲区连成一个环，或者由操作系统统一维护一个缓冲池。

缓冲池由操作系统集中管理缓冲区，进程按需借用，用完归还，避免各自零散申请。

这和信号量里的“许可牌”很像：缓冲区是有限资源，不能随便抢。

---

### 第五部分：假脱机技术

假脱机技术最典型的场景是打印。

打印机很慢，但用户程序不能一直卡在那等打印机吐纸。否则你点一下打印，整个系统就像被绑架了。

操作系统的做法是：

1. 用户程序把要打印的内容先交给磁盘上的输出井。
2. 用户程序以为“打印请求已经提交”，可以继续干别的事。
3. 后台打印进程慢慢从输出井里取任务，按顺序喂给打印机。

这就是假脱机。

它把独占设备改造成了“看起来可以共享”的设备。

打印机物理上一次只能服务一个任务，但很多用户可以把打印任务先排进队列。就像奶茶店只有一个出杯口，但所有人可以先拿号，后台按号制作。

考试如果问假脱机的核心作用，记住两点：

- 提高设备利用率。
- 把独占设备改造成逻辑上的共享设备。

#### 阻塞、非阻塞与异步 I/O

阻塞调用在暂时无法满足请求时使调用线程等待；非阻塞调用可立即返回已有数据或“暂不可用”，由程序以后重试。异步接口提交操作后返回，在完成时通过事件、回调或完成队列通知结果。

例如阻塞 `read` 会等待可读数据，非阻塞 `read` 在无数据时可返回暂不可用；异步读取提交后，完成通知再报告读入字节数。I/O 多路复用通常通知“哪些描述符已就绪”，程序随后再执行读写。设备使用中断还是 DMA，与应用接口是否阻塞是不同层次的问题。

### 第六部分：输入输出系统本章自测

**题 1：为什么中断控制比程序直接控制更高效？**

因为程序直接控制会让 CPU 一直等待设备完成，而中断控制允许 CPU 在设备工作期间去执行其他任务。设备完成后再用中断通知 CPU。

**题 2：直接内存访问为什么适合磁盘这类高速块设备？**

因为磁盘一次常常传输一大块数据。让 CPU 逐次搬运会占用较多处理器时间。直接内存访问能让控制器在设备和内存之间批量搬运，CPU 主要负责发起请求和处理完成通知。

**题 3：假脱机为什么能把独占设备改造成共享设备？**

因为多个进程不再直接抢打印机，而是把任务先排到磁盘队列里。后台进程再按顺序慢慢输出到打印机。物理设备仍然独占，但逻辑上多个用户都能提交任务。

## 第八章：文件管理

输入输出系统解决的是“设备怎么把数据送进来、送出去”，文件管理解决的是另一个问题：**这些数据长期放在硬盘上时，怎样让用户看到的是文件，而不是一堆冰冷的磁盘块。**

可以把文件系统理解成硬盘上的档案室。磁盘只提供格子，文件系统负责贴标签、建目录、记录位置、检查权限，让用户能用“文件名”和“路径”找到东西。

### 第一部分：文件系统到底在管什么？

文件系统解决的是：硬盘上只有一堆块，用户想看到的是文件和目录。

硬盘的物理世界是：

```text
块 0、块 1、块 2、块 3 ...
```

用户眼里的世界是：

```text
D:\项目\blog\source\_posts\OS笔记.md
```

文件系统的任务，就是把这些冰冷的块，组织成有名字、有路径、有权限、有结构的文件。

#### 1. 文件是什么？

文件是具有名字的一组相关信息的集合。

可以把它理解为下面这层意思。

**文件是操作系统承认的一份完整资料。**

比如：

- 一篇笔记。
- 一张图片。
- 一个程序。
- 一段视频。

这些在硬盘上可能都被切成很多块，但用户不需要知道。用户只需要知道文件名。

#### 2. 文件控制块

文件控制块是文件系统里的“户口本”。

它不一定保存文件内容本身，而是保存文件的管理信息，例如：

- 文件名。
- 文件类型。
- 文件大小。
- 文件在磁盘上的位置。
- 创建时间、修改时间。
- 访问权限。

考试经常拿它和进程控制块对比。

进程控制块是进程的身份证和病历，记录进程状态、寄存器、调度信息、打开文件等。

文件控制块是文件的户口本，记录文件名、位置、大小、权限等。

千万别混：进程控制块管“正在运行的程序”，文件控制块管“硬盘上的文件”。

#### 3. 目录是什么？

目录本质上也是一种特殊文件。

它里面保存的是“文件名到文件控制块”的映射关系。

你双击一个文件名时，操作系统会先查目录：

```text
这个名字对应哪个文件控制块？
这个文件控制块说数据块在哪里？
去那些数据块把内容读出来。
```

所以目录是一张索引表。

---

### 第二部分：路径名

#### 1. 绝对路径

绝对路径从根目录开始，一路写到目标文件。

例如：

```text
D:\项目\blog\source\_posts\OS笔记.md
```

它像完整家庭住址：哪个城市、哪条路、哪栋楼、哪一户，全都写清楚。

试卷里说“文件的绝对路径名由什么组成”，答案就是：

```text
从根目录到该文件所经历的全部目录名 + 文件名
```

不要只写文件名，也不要只写当前目录名。

#### 2. 相对路径

相对路径从当前目录开始。

如果你当前就在：

```text
D:\项目\blog
```

那么：

```text
source\_posts\OS笔记.md
```

就是相对路径。

相对路径像“从你现在的位置往前走两步左转”。它必须依赖当前所在目录。

---

### 第三部分：文件的逻辑结构与物理结构

#### 1. 逻辑结构：用户看到的样子

文件的逻辑结构是用户和程序眼里的组织方式。

常见有两类：

- **无结构文件**：就是一串字节流。很多普通文本、二进制文件都可以这样看。
- **有结构文件**：由一条条记录组成，比如学生记录、借阅记录。

逻辑结构回答的是：用户怎么理解这个文件。

#### 2. 物理结构：磁盘上怎么放

文件的物理结构回答的是：文件内容在磁盘块里怎么摆。

常见三种：

**连续分配：**

文件占用一段连续磁盘块。

优点是顺序访问极快，因为磁头可以一路读下去。

缺点是容易产生外部碎片，而且文件变大时很麻烦：后面如果没空位，就得搬家。

**链接分配：**

文件的数据块可以分散在磁盘各处，每一块里保存下一块的位置。

优点是不要求连续，文件增长方便。

缺点是随机访问很慢。你想读第 100 块，必须从第 1 块一路顺藤摸瓜找到第 100 块。

**索引分配：**

操作系统给文件单独准备一个索引块。索引块里记录这个文件所有数据块的位置。

优点是既不要求连续，又支持较快随机访问。

缺点是索引块本身要占空间；小文件可能显得有点浪费，大文件可能需要多级索引。

![同一文件采用连续块、后继指针链或独立索引块组织磁盘数据](/images/notes/operating-system/file-allocation-layouts.svg)

把它们放进生活直觉里：

- 连续分配像整本书页码连续装订。
- 链接分配像寻宝地图，每一页告诉你下一页在哪。
- 索引分配像目录页，先查目录，再直达目标页。

### 第四部分：打开文件的底层过程

为什么系统要有“打开文件”这个动作？为什么不能每次读写都从路径重新找？

因为从路径找文件很慢。

比如你要读：

```text
D:\项目\blog\source\_posts\OS笔记.md
```

操作系统要一级一级查目录：

```text
D: -> 项目 -> blog -> source -> _posts -> OS笔记.md
```

如果每读一小段内容都这么查一次，效率会很差。

所以第一次打开文件时，操作系统会：

1. 根据路径查目录。
2. 找到文件控制块。
3. 检查权限。
4. 把文件的关键管理信息放进打开文件表。
5. 返回一个文件句柄给进程。

之后进程读写文件时，不再每次从路径开始找，而是拿这个句柄直接访问打开文件表。

这就像你第一次去图书馆借书，要查书名、找书架、登记借阅；之后你手里有借书单，继续续借或归还就不用重新找整栋楼。

![首次打开按路径定位 FCB 并建立打开文件表项，之后读写通过句柄直接访问](/images/notes/operating-system/file-open-handle.svg)

### 第五部分：目录、链接与共享

单级目录要求所有文件名互不相同；两级目录为每个用户设独立目录；树形目录支持分层组织。共享会引入多个名字指向同一文件的关系，遍历时还需处理链接可能形成的环。

以 Unix 文件系统为例，目录项保存“文件名 → inode 编号”，inode 保存类型、大小、权限、数据块位置等元数据。文件名不必存进 inode，一个 inode 可以有多个目录项引用。

- **硬链接**是指向同一 inode 的另一个目录项。删除名字减少链接计数；最后一个硬链接移除、打开引用也释放后，空间才能回收。硬链接通常不能跨文件系统。
- **符号链接**保存目标路径，有自己的 inode，可跨文件系统，目标消失后会成为悬空链接。
- **挂载**把文件系统接到目录树的挂载点，使路径解析进入这个文件系统。

进程文件描述符表指向系统的打开文件描述，其中包含当前位置、打开方式等信息，再关联 inode。通过 `dup` 或继承而来的描述符可以共享当前位置；独立 `open` 通常有各自的当前位置。`close` 释放打开引用，`unlink` 删除目录项。

文件访问方式包括顺序访问、按偏移直接访问和按索引访问。用户看到的记录组织与磁盘块分配方式可以分别设计。链式分配还可把指针集中在 FAT 表中；索引分配可组合直接块指针、一级和多级间接索引，以兼顾大小文件。

### 第六部分：空闲空间、保护与一致性

#### 1. 空闲空间如何记录

| 方法 | 记录方式 | 使用特点 |
| --- | --- | --- |
| 空闲表／空闲区计数 | 起始块号和连续块数 | 适合连续空闲区，回收时合并相邻区 |
| 空闲链表 | 把空闲块或区串起来 | 单块分配直观，寻找大连续区较慢 |
| 位示图 | 每块对应一位 | 可按位扫描，容易寻找连续空闲块 |
| 成组链接 | 一组保存多块空闲块号，并链接下一组 | 批量取得空闲块号，减少逐块追链 |

例如每块 4KiB、共 1GiB 的分区有 $2^{18}$ 个块，位示图占 $2^{18}/8=32768$ 字节，即 32KiB。这里约定 0 为空闲、1 为已用；题目若使用相反约定，应按其定义计算。

#### 2. 权限与访问控制

访问控制矩阵用主体作行、对象作列，记录读写执行等权限；按对象存储可形成 ACL，按主体持有访问凭据可形成能力表。Unix 的所有者、组、其他用户权限是常见简化形式。

普通文件的读、写、执行对应读取内容、修改内容和执行程序；目录的读是列出名字，执行是沿名字查找和穿越，写是修改目录项。删除文件主要取决于父目录权限及附加规则，不能只看文件自身是否可写。

#### 3. 缓存、日志与崩溃一致性

写入通常先进入页缓存，成为脏页，随后回写。系统调用返回成功与数据已经持久化是不同事件；需要持久性时使用相应同步接口，并遵守文件系统对文件内容与目录更新的同步规则。

修改文件可能同时改变 inode、目录项和空闲位图。断电若只写完一部分，就会出现“块已占用但无人引用”等不一致。`fsck` 扫描和交叉检查结构；日志文件系统先记录更新，再按协议应用，崩溃后据日志恢复。写时复制文件系统把修改写到新位置，再切换引用。文件系统日志解决更新一致性，文件历史仍需通过备份保存。

### 第七部分：文件管理本章自测

**题 1：文件控制块和进程控制块有什么区别？**

文件控制块记录文件的管理信息，例如文件名、大小、位置、权限。进程控制块记录进程运行所需的管理信息，例如进程状态、寄存器、调度信息、打开文件。一个管文件，一个管进程。

**题 2：绝对路径名由什么组成？**

由从根目录到该文件所经历的全部目录名，以及该文件名组成。

## 第九章：磁盘存储器管理

文件管理站在用户角度看“文件怎么组织”，磁盘存储器管理则往下看一层：**磁盘这个慢速设备本身怎样读写才更快。**

这章要抓住磁头移动很慢这个物理事实，光背算法名字还不够。只要让磁头少来回跑，磁盘访问就会快很多。

### 第一部分：磁盘结构与磁盘访问时间

磁盘题看起来像数学题，其实先要理解物理动作。

磁盘读写一次数据，大致花三段时间：

1. **寻道时间**：磁头移动到目标磁道。
2. **旋转延迟**：盘片转到目标扇区。
3. **传输时间**：真正把数据读出来或写进去。

其中最容易被调度算法优化的是寻道时间。

因为磁头移动很慢。如果请求顺序乱七八糟，磁头就会在盘面上来回跑，像一个快递员在同一栋楼里一会儿跑 1 楼，一会儿跑 20 楼，一会儿又回 2 楼。

磁盘调度的目标就是：**少走冤枉路。**

---

### 第二部分：磁盘调度算法

#### 1. 先来先服务

最公平，谁先来处理谁。

问题是磁头可能疯狂来回跑。

例如当前磁头在 58，访问请求是：

```text
130, 42, 180, 15, 199
```

如果按先来先服务：

```text
58 -> 130 -> 42 -> 180 -> 15 -> 199
```

总移动距离就是每一段差值相加。

优点是公平，缺点是可能很慢。

#### 2. 最短寻道时间优先

每次选择离当前磁头最近的请求。

它像一个懒得走远路的快递员：先送离自己最近的那一单。

优点是平均寻道距离通常更短。

缺点是远处请求可能一直等。如果新来的请求总在磁头附近，远处那一单就可能被长期冷落。

#### 3. 扫描算法

扫描算法像电梯。

电梯不会因为楼下有人按了按钮就立刻掉头。它会沿着当前方向一直走，顺路服务请求，到头后再反向。

磁盘扫描算法也是这样：

1. 磁头沿当前方向移动。
2. 遇到沿途请求就处理。
3. 到达边界后再反向。

试卷里常给这种题：

```text
磁道号 0 到 199
当前磁头在 58
请求序列：130, 42, 180, 15, 199
当前方向：向内侧移动
```

如果约定 0 是最外侧，199 是最内侧，那么“向内侧”就是磁道号变大。

处理顺序：

```text
58 -> 130 -> 180 -> 199 -> 42 -> 15
```

移动距离：

```text
(130-58) + (180-130) + (199-180) + (199-42) + (42-15)
= 72 + 50 + 19 + 157 + 27
= 325
```

注意这里不要漏掉从 199 掉头到 42 的那一大段。很多人错就错在只算访问请求，不算磁头实际走过的路。

![磁头从 58 出发，FCFS 移动 647 个磁道，向大号扫描的 SCAN 移动 325 个磁道](/images/notes/operating-system/disk-scheduling-paths.svg)

#### 4. 循环扫描

循环扫描像单向环线公交。

它只朝一个方向服务，到达终点后直接回到起点，再继续同方向服务。

这样做的好处是等待时间更均匀，不会让某一端请求总是占便宜。

#### 5. LOOK 与 C-LOOK

LOOK 是扫描算法的改进。

普通扫描会一路走到磁盘边界，哪怕边界处没有请求也会走过去。

LOOK 更聪明：它只走到当前方向上最远的请求，然后掉头。

C-LOOK 则是循环扫描的聪明版：只在有请求的范围内循环，不一定跑到物理边界。

考试若没有特别说明，按题目要求使用指定算法，不要自己切换成改进版。

### 第三部分：磁盘存储器管理本章自测

**题 1：磁盘访问时间由哪几部分组成？**

主要由寻道时间、旋转延迟和传输时间组成。其中磁盘调度最主要优化的是寻道时间，也就是尽量让磁头少跑冤枉路。

**题 2：磁盘扫描算法为什么像电梯？**

因为它沿一个方向持续移动，顺路处理请求，到边界或最远请求后再掉头。它不会因为反方向来了一个请求就立刻乱掉头。

### 第四部分：磁盘初始化、SSD 与 RAID

磁盘投入使用涉及设备级格式、分区、建立文件系统以及挂载。现代硬盘的底层格式通常由厂商完成；用户格式化主要建立文件系统元数据。启动过程由固件、引导程序加载操作系统。坏块可由设备控制器重映射，也可由文件系统记录并避开。

机械磁盘平均访问时间可写为：

$$T=T_{seek}+T_{rotation}+T_{transfer}$$

转速为 7200rpm 时一周约 8.33ms，均匀随机到达时平均旋转等待约 4.17ms。C-SCAN、C-LOOK 的回程虽然不服务请求，计算实际磁头移动距离时仍要计入。

**SSD 没有磁头寻道。** 闪存按页读写、按更大的擦除块擦除，更新常写到新位置，由 FTL 维护逻辑地址映射。垃圾回收整理有效页并擦除旧块，磨损均衡分散擦写次数，TRIM 告知设备哪些逻辑块已无需保留。机械盘的磁道扫描算法不能直接解释 SSD 的性能。

RAID 用多个设备组织条带、镜像或校验。在各盘容量均为 $C$ 时：

| 级别 | 组织方式 | 可用容量与失效容忍 |
| --- | --- | --- |
| RAID 0 | 条带，无冗余 | $nC$；任一盘失效可能破坏整个卷 |
| RAID 1 | 镜像 | 两盘镜像可用 $C$，容忍其中一盘失效 |
| RAID 5 | 分布式单校验 | 至少三盘，可用 $(n-1)C$，容忍一盘失效 |
| RAID 6 | 分布式双校验 | 至少四盘，可用 $(n-2)C$，容忍两盘失效 |
| RAID 10 | 镜像后条带 | 偶数盘且至少四盘，可用 $nC/2$；每个镜像组至少保留一盘才能继续服务 |

RAID 提高可用性，但误删和错误写入也会同步进入阵列，历史版本与独立副本仍由备份提供。

## 复习路径与参考资料

沿着一次程序运行串起各章：系统调用进入内核 → 创建进程和线程 → 调度 CPU → 同步共享数据 → 建立地址映射与处理缺页 → 发出 I/O → 通过文件系统定位设备上的数据。每个环节分别检查数据结构、状态变化、算法选择与性能代价。

- [Operating Systems: Three Easy Pieces](https://pages.cs.wisc.edu/~remzi/OSTEP/)：按虚拟化、并发和持久化组织进程、内存、同步与文件系统内容。
- [Linux man-pages](https://www.kernel.org/doc/man-pages/)：可查 `fork`、`execve`、`wait`、`open`、`mmap` 等接口的具体语义。
